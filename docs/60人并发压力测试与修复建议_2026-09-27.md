# 60 人并发压力测试与修复建议

测试日期：2026-09-27。本文是当前部署版本的实测报告，不是修复完成或正式实验验收证明。

## 1. 结论与优先级

**当前版本不应直接开展 60 人集中参与的 H/HA 混合预实验。**

存在两个独立问题：

| 优先级 | 问题 | 实测证据 | 处理要求 |
| --- | --- | --- | --- |
| P1，阻塞实验 | 同一 Session 含 H 和 HA 时，零 LLM 的 H 组被误判为 API 决策仍在等待 | H 组 30 份人工决策全部保存，但 `results_ready=False`；三个 HA 组均已完成；服务器最小复现测试失败 | 先补回归测试，再修复零 API Agent 分支 |
| P1，影响计时公平性与体验 | Web 请求排队明显，页面切换耗时占用统一决策窗口 | 60 个结果页平均约 8 秒、最慢约 16 秒；准备页单批约 28 秒；集中准备流程中部分决策页已被重定向 | 分析每请求开销，优化同步与结果页面，再复测 |

服务器没有在本轮测试中崩溃。纯 Human 两个测试轮的结算与重复读取核验通过，已结算 HA 组的数据核验也通过。**这些通过项不能抵消 H 组永久等待和页面延迟问题。**

本轮没有修改生产实现，没有部署修复，也没有重启生产服务。后续由本地修改、测试通过后再同步服务器。

### 准备到决策的集中切换风险

另一个集中批次测试包含两批 RoundStartSync GET、一批准备页 POST 和一批 Decision GET：

- 第一批准备页 GET 整批约 28.07 秒，平均 14.40 秒，最大 28.01 秒。
- 第二批准备页 GET 整批约 27.61 秒。
- 准备页 POST 整批约 21.07 秒。
- 随后 60 个 Decision GET 中，10 个返回 200，50 个被 302 重定向；当时部分组已经达到统一 60 秒截止时间。

这是合成集中批次流程，并非真实浏览器连续操作的完整复刻。但它足以说明：**在当前串行队列下，统一计时可能先开始，而排在后面的客户端还没有取得决策页面，实际可决策时间会被页面切换和请求排队消耗。** 50 个重定向不是 50 个 HTTP 500，也不等价于真实实验必然有 50 人掉线。

## 5. 数据与 DeepSeek 核验

### 纯 Human 两轮

- 每轮 60 份人工决策均已保存，决策来源为 manual，两组均 `results_ready=True`。
- 人数、出发分布计数、同一分钟批次数量、排队时间、到达时间、早到/迟到、总成本和收益均通过独立算式核对。
- 独立重算没有调用生产结算函数作为答案；同一分钟的主体按当前代码的整批服务规则计算，等待为继承等待加 `批人数 / 服务率`。

## 6. 当前并发处理逻辑

### HTTP 和数据库事务

当前服务器 oTree 的生产入口使用一个 Uvicorn worker。`CommitTransactionMiddleware` 对请求执行 `async with lock2`，锁内创建数据库会话并完成请求处理；响应状态小于 500 时 commit，否则 rollback。

因此 60 个请求可以同时建立连接并等待，但业务请求和数据库事务在这个 worker 内按锁串行执行。它有助于减少共享 ORM 状态和页面推进竞态，却意味着页面工作量会累积成明显排队时间。增加服务器 CPU 核数不会自动使这个请求通道并行。

### 实验组结算

实现位于 `dynamic_bottleneck_round/__init__.py`：

- `maybe_start_round`（约 1687 行）：按组判断需等待的 Human 是否到齐，或准备截止是否到达；开始后设定统一 60 秒决策截止。
- `maybe_prepare_results`（约 2107 行）：全部 Human 已有选择时尝试结算；达到截止时补齐缺失选择再结算。
- `set_results` / `try_group_results_lock`（约 1950–1976 行）：使用非阻塞 `fcntl.flock`，锁键包含 Session、组和轮次，保护跨进程同一组的结算。
- `_set_results_locked`：已 `results_ready` 时直接返回；收集 Agent 决策、统一计算队列和收益，保存反馈、更新 Agent 状态，最后标记就绪。
- `ResultsSync`（约 4132 行）及其模板：尚未就绪时整页刷新，基础间隔 1.5 秒；就绪后约 200 ms 自动 POST 前进。

这里的 1.5 秒是响应之后客户端等待再刷新，并非保证服务器每 1.5 秒处理完所有人的轮询。当前测试中单批请求本身远超过这个间隔。

### LLM 与 RL

- `_API_AGENT_PREFETCH_EXECUTOR` 最多同时处理 8 个组级任务；每个组内部 `choose_api_agent_departures` 再开线程，按该组 LLM 数并发调用，正式 HA 组为 10 个。
- `prefetch_coordinator` 使用非阻塞文件锁、已开始标记和原子发布的 JSON 缓存，使同一主机同一用户的 Web/超时进程共享同组同轮的 API 结果，减少重复外部调用。
- `collect_api_agent_prefetch` 校验共享结果数量及有效选择，失败时按配置进行本地兜底。
- RL 在本地准备决策，不调用 DeepSeek；结果就绪后统一更新相关学习状态。
- 组级任务池 8 不等于全站仅允许 8 个外部 API 请求，也不是提供商限流保护。本轮实际有三个 HA 组，每组 10 个 LLM。

不能未经共享状态、锁及数据库事务设计核验，就简单将 Web worker 改成 60 个；现有进程内请求锁不是跨 worker 的全局事务锁。

## 7. 功能缺陷根因与建议修复

主要定位点：`dynamic_bottleneck_round/__init__.py` 的 `collect_api_agent_prefetch`，约 3044–3062 行；上游 `start_api_agent_prefetch`，约 2980–3015 行；调用方 `_set_results_locked`，约 1982 行。

当前执行链：

1. 混合 Session 含 HA 组，所以会话级 `api_agent_mode` 为 active。
2. H 组的 API Agent 数为 0，没有已保存的 API 决策。
3. `start_api_agent_prefetch(H组)` 得到空 prepared_agents，释放 claim 后返回 None；这是“没有任务”，并非“有任务未完成”。
4. `collect_api_agent_prefetch` 没有针对该组 0 API Agent 提前返回 []，而将“无 payload 且无 task”解释为 `API_AGENT_DECISIONS_PENDING`。
5. `_set_results_locked` 因 Pending 返回 False，不设置 `results_ready`。
6. 不存在能使它变成就绪的 API 请求，反复刷新也不能解决。

**修改要求：按组判断是否需要 API，而不是只判断整个 Session 的 API 模式。**

建议先在 `test_dynamic_agent_integration.py` 增加失败用例，再改实现：

- 会话级 API active、当前 H 组 API 数为 0：收集器必须返回 []，不能返回 Pending；不得发起 API 请求。
- 同一混合 Session 中，H 组人工决策完成后能结算；HA 组仍等待自己的 API，不混用其他组记录。
- API 数为 0、RL 数大于 0 的小组：只准备和结算本地 RL，不等待不存在的 API。
- 有 API Agent、任务尚未完成的组：仍返回 Pending，不能提前用空列表结算。
- 有 API Agent、任务成功/失败的组：保留现有缓存、校验、兜底和防重复机制。
- 多次页面刷新或收集不重复外部调用、不重复 RL 更新、不重复收益结算。

最小修复方向是在收集器开始位置对当前组 API 数为 0 返回 []；预取入口也可添加同样的早返回，避免无效锁/文件操作。不要为规避问题取消 H 组，不要把 H 组伪装成有 LLM，不要修改服务率或结算公式。

已保存可复现的最小测试：`output/concurrency60_20260927/zero_llm_reproduction.py`。在当前本地和服务器代码上该条件均失败；失败是刻意要求正确行为的回归断言，不是网络问题。该测试不访问数据库、不调用 API。

从项目根目录可运行：

```bash
PYTHONPATH=. python output/concurrency60_20260927/zero_llm_reproduction.py
```

这是定位用最小测试，不替代使用真实分组配置的集成测试。既有 323 项测试曾通过，但本轮发现的新场景未被它们充分覆盖；本次没有重新运行整个既有测试套件。

## 8. 性能问题的证据与优化顺序

最终定向测试共采样 206 次：

| 指标 | 观测值 |
| --- | --- |
| Web/超时服务进程 RSS 合计峰值 | 149.58 MiB |
| PostgreSQL 总连接采样峰值 | 10，包含监测连接及其他服务器连接 |
| 主机 MemAvailable 最低值 | 约 942.80 GiB |
| 采样服务 CPU 最大值 | 约 83.30%，以一个 CPU 核 100% 为口径 |
| 最终服务状态 | active |
| 实际实验端口登录健康检查 | HTTP 200，server: uvicorn |

资源指标与单 worker 全局请求锁共同表明：本轮没有看到内存或数据库连接耗尽，主要风险在请求通道的串行排队和单次页面工作量。**尚未进行函数级 CPU/SQL 剖析，不能把所有耗时归因于某一个函数。**

建议优化顺序：

1. 先修复零 API 组的永久等待，并补齐混合分组集成回归。
2. 记录准备页、Decision、ResultsSync、Results 的服务端处理耗时、SQL 数量、重复读取/序列化和模板计算开销；不要只看 CPU 总体利用率。
3. 优先减少同步轮询的完整页面工作量；可评估轻量只读状态接口、退避与随机抖动，避免全体同时刷新。只读接口若绕过请求锁，需要单独设计安全数据库会话，不能共享当前 ORM 请求会话。
4. 将每组每轮可共享的分布/成本汇总提前缓存，避免每个参与者查看 Results 时重复执行同样的聚合、反序列化和计算。
5. 检查统一截止计时与客户端拿到决策页的时间差，以及截止附近已入队但尚未处理的提交；不要未经实验设计确认随意延长正式决策时间或改变选择规则。
6. 再评估是否需要多 worker、共享协调与按组事务策略；不是直接加 worker 或加 CPU 后宣称修复。

建议复测目标（待确认的工程验收目标，不是本轮已达成结果）：60 并发下同步查询及结果读取 P95 尽量不超过 2 秒；无 5xx、无永久等待；有效决策和主体数量准确；重复提交/读取不重复结算；网络与实际浏览器流程中的决策截止公平性可接受。

## 9. 本地修复后的验证与同步

本地阶段：

- 先将上述零 API 回归从失败改到通过，并保留有 API 场景的 Pending 行为。
- 运行动态瓶颈单元、随机容量、Agent 集成、RL、预训练经验库、prefetch 协调、问卷、支付与房间兼容回归。
- 若修改同步接口或页面计时，增加自动刷新、迟到请求、截止边界和重复 POST 的测试。
- 不修改随机服务率生成、排队数学规则、Agent 实验策略或历史数据库以“让压测通过”。

服务器同步后：

- 保留生产环境变量和已有实验数据，确认没有真实实验正在进行，再部署并重启。
- 新建测试 Session，重复纯 H 分散/集中场景和 H/HA 混合场景。
- 混合场景必须所有组均就绪，包含当前 H 组；不能只核验三个 HA 组后宣称全会话通过。
- 使用真实客户端从登录到结果、问卷和报酬完整跑通，再开展持续 33 轮及校园网多终端测试。
- 使用新建含 RL 的 Session；本轮跳过历史轮次的测试会话不得用于预实验。
