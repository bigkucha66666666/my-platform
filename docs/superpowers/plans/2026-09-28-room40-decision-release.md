# 每房间 40 人同步放行本地实施计划

> 本计划对应已确认的 `../specs/2026-09-28-room40-decision-release-design.md`。仅改本地代码与测试，不部署、不创建真实 API 成本。用户随后授权本地隔离服务重启和名为“并发改进”的 Git 提交。

## 目标与不可变条件

- 一个 Session 内 G01/G02 共用每轮放行时刻和 60 秒截止；不同 Room/Session 完全隔离。
- 决策页先完整加载、ACK 后才放行。I1 本轮真实服务率不得出现在放行前 HTML/响应，I0 决策前不得知真实值。
- 只有服务器确认在窗口内收到的合法人工选择才标记 `manual`；截止前已进入但排队中的提交不能被自动补选覆盖。
- 不能将技术故障伪装为被试缺席；异常轮次须可审计、可排除。旧 Session 继续旧流程。

## 2026-09-29 本地验证记录与上线阻断项

- 361 项动态场景 Python 测试通过；`room_release.cjs` 与 `sync_poll.cjs` 的 7 项脚本检查通过。补测覆盖已保存选择但 POST 仍在途、ACK/POST 清空超限、具体 GET/POST 响应时间匹配。测试没有覆盖真实 40/80 人浏览器延迟。
- 在独立临时目录创建全新 SQLite 演示 Session，不触碰项目现有数据库，也不启用 API Agent。`project_asgi:app` 在获得本地端口绑定权限后可启动；普通沙箱下端口绑定报 `Operation not permitted`。
- 用户已在现有 Chrome 手动允许本机测试地址；隔离 Session 的单人页面实际进入 Decision、提交到 Results，相关静态资源返回 200。自动化浏览器控制接口仍超时，因此这一证据仅为单人手动走查；新版 GET 令牌关联正在复验，40/80 人并发和 33 轮浏览器彩排仍未完成。正确入口为 `/InitializeParticipant/{code}`，不能把直接 `/p/{code}` 的 404 当作业务页面测试结果。
- 导出的 `room_release_shell_get_ingress_ts` 是服务器收到 GET，`room_release_shell_render_started_ts` 是开始构造模板上下文，`room_release_shell_response_completed_ts` 是该浏览器 ACK 对应 GET 的服务器响应完成；`room_release_operative_ts` 只是服务器处理浏览器“已可操作”报告的时刻，不能证明显示在所有设备同一毫秒发生。
- 额外在全新隔离 SQLite 中，以两个独立 Session（I0、I1）各 40 名 Human、每 Session 两组 30＋10，运行同机 HTTP＋WebSocket 并发彩排。两个 Session 均关闭 API/RL Agent；GET 决策壳页 80/80 返回 200，80/80 ACK 后各 Session 独立形成 T；服务端收到“已可操作”报告相对各自 T 的 P95 为 0.510 秒、最大 0.527 秒；80/80 人工决策 POST 返回 302，P95 为 0.464 秒、最大 0.488 秒；80/80 结果页返回 200 且 ready，四组分别记录 30、10、30、10 个 `manual` 选择，组内共同开始/截止完全一致，无技术异常。这个彩排没有真实浏览器渲染/静态资源下载、真实 HA Agent、网络差异或连续 33 轮，因此不能替代正式门槛。
- 本地压测用的 `DYNAMIC_ROOM_RELEASE_DRAIN_SECONDS=10` 仅是隔离测试参数，不是经正式负载分布确定的上线阈值；生产 `Procfile` 和协议开关保持原状。
- 当前 `otree prodserver` / `Procfile` **未切换**到新入口。正式协议开关保持关闭；只有经批准切换到保留单 worker 与 timeout 子进程的 `project_prodserver.py`、实测确定请求清空阈值，并通过真实浏览器延迟门槛后才能启用。

## 2026-10-07 修复与证据更正

- 10 月 7 日服务器报告确认：标准初始化后的冻结 Player 会拒绝 `_room_release_choice_preexisting` 临时属性，真实 Decision GET 为 500。上述 9 月 29 日直接 ASGI 彩排没有证明标准初始化入口有效，其 80/80 结果不能当作正式启用依据。
- 临时“表单填充前已有选择”改为每请求 ContextVar 字典，跨同步线程共享同一请求的首值，但跨请求、参与者和轮次隔离；异常退出也清理。没有关闭模型冻结或新增数据库列。
- 启动器在导入应用前设置 `USE_TIMEOUT_WORKER=1` 并调用 `otree.main.setup()`；ASGI 入口拒绝没有初始化的加载方式。保留单 worker 和 timeout 子进程。
- 前端使用带每页面随机标识的往返时钟区间及 `performance.now()`；服务器仅回显标识，不信任客户端时间。按服务器时间上界关闭输入、按下界等待自动提交，防止延迟回包重新开放截止窗口，也避免过早默认值被计为 manual。刷新/多标签页的回复不能相互校时，旧空窗口快照不能清除已知截止，技术异常一旦收到就停止本页流程。
- 新增 `test_room_release_framework.py`，使用全新临时数据库及标准初始化的冻结模型，覆盖真实 GET、合法/非法/提前/晚到/旧页面/排队 POST、下一轮、40/80 人 LiveConsumer、I0/I1 边界、HA 的真实 RL 与模拟 LLM、刷新与重连。
- 本地真实 Chrome 验收与最终结果另记于本次修复报告。生产启动命令、协议开关、数据库和正式房间未在本次任务中改变。
- 最终本地记录：373 项动态回归（372 通过、1 项全流程默认跳过，另在 oTree 5.11.5 显式通过）、98 项专项回归与 7 项 JS 检查；80 人真实框架 33 轮、2640 manual、H/HA 问卷及成本/现金复算通过。真实 Chrome 的单房间 40 人一轮、双房间 80 人六轮通过；因用户反馈 CPU 温度高及时退出压测，80 人全 33 轮浏览器及目标服务器验收仍未完成，不勾选完整浏览器验收项。详见 `../../并行机制改进_本地修复与验收_2026-10-07.md`。
