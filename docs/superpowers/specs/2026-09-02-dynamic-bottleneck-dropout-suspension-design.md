# 动态瓶颈连续掉线暂停设计

## 目标

连续两轮没有人工有效提交的参与者进入暂停状态，不再拖延后续轮次的到齐检查；系统仍为其生成代理选择，保持实验中的车辆数量不变。参与者返回后必须在恢复页确认，并从后续尚未完成的轮次恢复人工决策。

## 状态与选择

- 人工成功提交会把连续未提交计数清零，并保存为最近一次人工选择。
- 超时或截止时未提交会把连续未提交计数加一；同一轮重复汇总不得重复计数。
- 连续未提交达到 2 轮后，参与者进入暂停状态。
- 暂停参与者不计入轮次准备人数；本轮开始时立即生成代理选择。
- 自动选择优先沿用最近一次人工选择；没有历史人工选择或该时间不在当前范围内时，使用准时到达所需的中性出发时间。
- 自动选择继续进入排队和成本计算，并通过 `decision_source` 与逐轮审计字段和人工选择区分。

## 恢复与数据

- 暂停状态沿用现有 `RecoveryGate`，必须由参与者点击确认，不自动恢复。
- 恢复不会修改已经完成轮次的自动选择。
- 连续未提交计数、暂停状态和自动选择策略保存在 `participant.vars`，逐轮快照加入自定义导出；不新增数据库字段。
- 热身轮也执行恢复机制，但仍按现有规则从正式自定义数据中排除。

## 边界

- 暂停参与者仍作为代理车辆参与拥堵，避免实际瓶颈人数突然变化。
- 本设计不加入浏览器网络心跳，也不把切换标签页直接判定为掉线。
- 如果整组均离线，oTree 仍需下一次页面请求才能推进，这是请求驱动框架的固有限制。
