# 均匀分布随机服务率与 I0/I1 信息处理后端改造交接文档

## 1. 文档用途

本文档用于将现有 `dynamic_bottleneck_round` 从“事故是否发生 + Beta 容量损失”改造为“每轮服务率直接从均匀分布中抽取”的随机单瓶颈实验。本文档是交给后续开发任务的需求与验收依据，不表示当前代码已经完成改造。

实现时保留现有的单瓶颈排队、早到/迟到成本、Human/LLM/RL 主体构成和 2 x 2 组间设计，仅替换容量生成机制、信息条件和与事故相关的上下游逻辑。

## 2. 研究场景

每轮代表一个工作日的早高峰通勤。所有主体从家中出发，经过同一个固定关键瓶颈后到达单位。瓶颈可以解释为过江隧道入口、高架汇入口、桥梁入口或进城方向道路收窄处。

瓶颈位置与物理结构不变，但交通组成、驾驶行为、车头时距、天气、控制状态和其他未观测运行条件使其有效通过能力存在日际变化。因此，新场景不再为每一次服务率变化指定某一场事故，而是将其定义为“当日有效瓶颈服务率”的随机性。

同一轮内的服务率保持不变，不同轮之间变化。同一实验组的所有主体在当轮面对同一服务率。

## 3. 文献参数化

主实验采用 Liu et al. (2023) 的随机单瓶颈实验设定：

$$
\mu_r \sim U(1.33, 4.00),
$$

其中，$\mu_r$ 是第 $r$ 个正式轮次的瓶颈服务率，单位为“主体/分钟”。

理论分布统计量为：

$$
E(\mu_r)=\frac{1.33+4.00}{2}=2.665,
$$

$$
\operatorname{SD}(\mu_r)
=\frac{4.00-1.33}{\sqrt{12}}
\approx 0.771.
$$

引用信息：

> Liu, Q., Lu, D., Jiang, R., Han, X., Liu, R., & Gao, Z. (2023). Departure time choice behavior in commute problem with stochastic bottleneck capacity: Experiments and modeling. *Transportmetrica A: Transport Science, 19*(2), 1978590. <https://doi.org/10.1080/23249935.2021.1978590>

开放全文：<https://eprints.whiterose.ac.uk/id/eprint/178499/1/Liu%20Q%20et%20al%20-%202021TransportmetricaA%20-WRR.pdf>

论文中应称为“根据既有随机瓶颈实验进行参数化”或“服务率从给定均匀分布中抽取”。在没有使用道路实测数据估计参数时，不应称为“拟合中国现实服务率”。

## 4. 服务率序列

### 4.1 生成原则

- 练习轮与正式轮分开；练习轮不进入正式数据、RL 正式学习和实际支付。
- 每个正式轮只有一个正值 `actual_capacity`。
- `actual_capacity` 直接从 $U(1.33,4.00)$ 生成，不再先抽取事故布尔变量，也不再抽取容量损失率。
- 生成器先从连续均匀分布抽样，再四舍五入到两位小数；该两位小数是当轮正式 `actual_capacity`。
- 同一 `actual_capacity` 同时用于排队结算、Human 页面、LLM 提示词和 RL 决策输入，避免 Agent 因获得更多小数位而产生额外信息优势。
- 序列一旦用于正式 Session，不得根据中途结果替换、重抽或调整。

### 4.2 短轮次的分布覆盖

正式轮次较少时，纯粹独立抽样可能使某条序列偶然集中在分布中部。正式序列库推荐使用随机化的等概率分层抽样：

1. 将 $U(1.33,4.00)$ 的累积概率区间按正式轮数 $R$ 分为 $R$ 个等概率层。
2. 每层独立抽取一个服务率。
3. 使用固定随机种子对 $R$ 个值的轮次顺序进行随机打乱。
4. 将序列冻结到可审计的 JSON 序列库中。

这保证一条短序列覆盖从低到高的容量区间，同时保留轮次顺序的不可预测性。需要在方法部分如实说明这是“随机化分层序列”，不应将整条序列说成完全独立同分布样本。

如果研究者要求严格 i.i.d. 抽样，则可以保留纯随机生成器，但应使用多条冻结序列并将序列作为分析中的区组。不得在看到实验结果后挑选更容易得到某一结论的序列。

### 4.3 组间匹配

同一 Session 内的独立 Group 在同一正式轮应使用同一条序列的同一服务率。各 Group 的出发选择、队列、成本、Agent 状态和收益仍彼此独立。

多个实验场次应轮换使用多条预先冻结的序列，并保证每条序列在 H-I0、H-I1、HA-I0 和 HA-I1 中使用次数一致或尽量平衡。

## 5. 2 x 2 处理设计

| 处理 | Human | LLM | RL | 决策前容量信息 |
|---|---:|---:|---:|---|
| H-I0 | 30 | 0 | 0 | 只知道服务率分布 |
| H-I1 | 30 | 0 | 0 | 知道分布和当轮精确服务率 |
| HA-I0 | 10 | 10 | 10 | 只知道服务率分布 |
| HA-I1 | 10 | 10 | 10 | 知道分布和当轮精确服务率 |

oTree 的 Session 登录人数只计算 Human，不包含后台 LLM 和 RL Agent。当前每组 30 个总主体的构成保持不变。

## 6. I0/I1 信息条件

### 6.1 I0：只知道分布

I0 在当轮决策前可见：

- 服务率服从 $U(1.33,4.00)$；
- 服务率的可能范围为 1.33 至 4.00 主体/分钟；
- 区间内各等长子区间等概率；
- 截至上一轮已公开的历史反馈。

I0 在提交当轮出发时间前不得获得：

- 当轮 `actual_capacity`；
- 当轮容量等级；
- 任何由当轮服务率派生的提示、颜色、文字或图标；
- 当轮其他主体的选择。

决策页建议文案：

> 本轮服务率将在所有人完成选择后公布。

### 6.2 I1：决策前知道精确服务率

I1 拥有 I0 的全部信息，并在提交出发时间前额外获得当轮 `actual_capacity`。

决策页建议显示：

> 本轮瓶颈服务率：2.37 主体/分钟  
> 通行能力等级：中等

容量等级只是帮助 Human 理解数值的确定性表达，不是新的实验处理。建议使用均匀分布的三个等概率区间：

| 标签 | 服务率范围 |
|---|---|
| 低 | $1.33 \leq \mu_r < 2.22$ |
| 中 | $2.22 \leq \mu_r < 3.11$ |
| 高 | $3.11 \leq \mu_r \leq 4.00$ |

标签必须完全由 `actual_capacity` 和固定阈值生成，不得由管理员临时选择。I1 的主要实验信息仍是精确服务率数值。

### 6.3 事后反馈保持一致

所有主体完成当轮选择并结算后，I0 和 I1 获得相同的事后反馈：

- 当轮真实服务率；
- 匿名出发时间分布；
- 匿名分时成本或项目已批准的群体反馈；
- 主体自己的排队、到达、早到/迟到、成本和收益。

这使两个信息组的主要处理差异集中为“真实服务率是否在出发时间决策前已知”，而不是事后反馈量的差异。

### 6.4 现实解释

I1 应在论文中定义为“完全出行前容量信息”或“高精度出行前预测的理论上限情景”。不应宣称现实导航系统能够无误差地观测真实服务率。

若后续要研究更贴近现实的预测，应单独增加“噪声预测”处理，不应在本次 I1 中临时添加未预注册的预测误差。

## 7. 新后端数据结构

### 7.1 建议配置字段

```text
capacity_distribution = uniform
capacity_min = 1.33
capacity_max = 4.00
capacity_sequence_id = S01
capacity_sequence_seed = <frozen integer seed>
capacity_information_condition = I0 | I1
```

正式配置必须校验：

- `capacity_distribution` 只允许 `uniform`；
- `capacity_min` 必须等于 1.33；
- `capacity_max` 必须等于 4.00；
- `capacity_min < capacity_max`；
- `capacity_information_condition` 只允许 I0 或 I1；
- 正式 Session 只能使用已批准的冻结序列，不得使用不可审计的临时自动序列。

### 7.2 每轮序列记录

```json
{
  "formal_round_number": 1,
  "actual_capacity": 2.37,
  "capacity_level": "medium",
  "sequence_id": "S01",
  "sequence_seed": 2026091101,
  "distribution": "uniform",
  "capacity_min": 1.33,
  "capacity_max": 4.0
}
```

`capacity_level` 可以在读取时由 `actual_capacity` 派生，无需作为独立的权威数据源。如果 JSON 中保存该字段，加载时必须验证它与数值阈值一致。

### 7.3 需要删除的事故概念

正式运行路径不再使用：

```text
incident_occurred
accident_probability
capacity_loss_ratio
remaining_capacity_ratio
accident_normal_capacity
accident_loss_alpha
accident_loss_beta
accident_information_condition
```

与事故状态有关的页面文案、序列生成、后台校验、Agent 提示词、导出列、管理页摘要和问卷提示应同步更新。

不得将旧 `accident_information_condition=I1` 静默映射为新 I1，因为旧 I1 只知道事故布尔状态，新 I1 知道精确连续服务率，两者的信息含义不同。旧字段出现在新正式配置时应立即报错。

## 8. Human、LLM 和 RL 的信息一致性

后端应使用单一的公开上下文构造函数，再将相同的公开字段分别转换为 Human 页面、LLM 提示词和 RL 决策输入。

### 8.1 I0 决策上下文

```json
{
  "information_condition": "I0",
  "distribution": "uniform",
  "capacity_min": 1.33,
  "capacity_max": 4.0,
  "current_capacity_revealed": false
}
```

I0 的决策上下文中不得出现 `actual_capacity`、`capacity_level` 或任何当轮容量的可逆派生量。

### 8.2 I1 决策上下文

```json
{
  "information_condition": "I1",
  "distribution": "uniform",
  "capacity_min": 1.33,
  "capacity_max": 4.0,
  "current_capacity_revealed": true,
  "actual_capacity": 2.37,
  "capacity_level": "medium"
}
```

Human、LLM 和 RL 必须在同一处理中获得相同的容量信息。它们可以使用不同的内部学习和推理方式，但 Agent 不得通过序列库、Group 隐藏字段或审计日志获得未对 Human 公开的信息。

## 9. Liu-REL RL Agent 修改要求

当前事故版 I1 根据“事故/无事故”布尔状态筛选历史经验。新 I1 接收的是连续服务率，因此不能保留二元事故筛选逻辑。

### 9.1 I0 RL

- 决策前不读取当轮 `actual_capacity`。
- 使用所有已结算的正式历史经验更新各出发时间的成本倾向。
- 练习轮不进入正式经验库。

### 9.2 I1 RL

I1 RL 在决策前接收当轮精确服务率，并对历史经验按容量相似度加权。推荐复用项目早期 I2 连续容量高斯核的思路，但重新命名为新 I1 完全信息策略：

$$
w_j(\mu_r)
=\exp\left[-\frac{(\mu_r-\mu_j)^2}{2h^2}\right],
$$

其中，$\mu_r$ 是当轮服务率，$\mu_j$ 是历史经验 $j$ 的服务率。带宽使用均匀分布的理论标准差：

$$
h=\operatorname{SD}(\mu_r)
=\frac{4.00-1.33}{\sqrt{12}}
\approx 0.771.
$$

该参数来自预先声明的容量分布，不根据正式实验结果调整。可在正式实验前进行不使用正式被试数据的算法敏感性检查，但必须在预注册中冻结最终带宽。

如果加权后有效历史覆盖不足以支持至少两个不同出发时间，整体回退到 I0 的全部历史经验。如果 I0 历史仍稀疏，则按既有预先冻结的均匀探索规则处理。

### 9.3 算法公平性

- I0 和 I1 使用相同的 Liu-REL 倾向更新、出发时间插值/外推和 Softmax 规则。
- 两组使用相同的 $\lambda$、$\eta$、初始探索轮数和训练预算。
- 唯一信息差异是 I1 可以用当轮服务率对历史经验加权，I0 不可以。
- 每个 RL Agent 保留独立状态和随机流，不得共享未公开的个体经验。

新策略版本应使用不含 `incident` 的新名称，例如：

```text
dynamic_liu_rel_uniform_capacity_v1
```

## 10. LLM Agent 修改要求

I0 的 LLM 提示词应说明均匀分布范围和已公开历史，但不得包含当轮真实服务率或容量等级。

I1 的 LLM 提示词在相同信息基础上增加：

```text
本轮瓶颈服务率为 2.37 主体/分钟，容量等级为中。
```

LLM 的决策提示词不得包含未来服务率、当轮其他主体选择、未公开的 Agent 类型或完整序列库。调用失败时的备用策略也必须使用同一信息边界。

## 11. 页面与文案改造

至少检查并更新：

- `Introduction.html`：从事故风险改为通勤日有效服务率的均匀分布。
- `FormalStart.html`：说明正式轮数、分布范围和本组信息条件。
- `Decision.html`：删除“本轮发生/未发生事故”；I0 显示尚未公布，I1 显示精确服务率和辅助等级。
- `Results.html`：I0/I1 都显示当轮真实服务率，不再显示事故概率、损失比例和剩余容量。
- 管理员 Session 创建页：用新的 H-I0、H-I1、HA-I0、HA-I1 含义替换事故版摘要。
- 数据导出、管理报告和事后问卷：清理事故用语，改为服务率分布和出行前容量信息。

页面的中文单位必须与实验说明一致。如果当前页面使用“车/5分钟”而模型内部使用“主体/分钟”，必须统一换算和说明，不得仅替换文字而保留不一致的数值。

## 12. 轮次与练习

本次改造默认保留当前已批准的轮次设定：

- 5 轮练习；
- 30 轮正式实验；
- 总轮数 35。

如果后续减少正式轮数，必须同步更新序列长度、支付结算、页面轮号、数据导出、RL 停止学习条件和自动化测试。不允许通过对 30 轮数组简单切片来默默运行较短实验，必须生成对应轮数的新冻结序列并完整审计。

练习轮可使用预先固定的服务率，并对所有处理公开，用于帮助参与者理解小数服务率、队列结算和信息页面。练习轮页面必须明确标记“练习”，避免 I0 参与者误以为正式轮也会在决策前公布容量。

每个正式轮至少导出：

```text
formal_round_number

information_condition
capacity_distribution
capacity_min
capacity_max
capacity_sequence_id
capacity_sequence_seed

departure_time
queue_delay
arrival_time
schedule_early
schedule_late
total_cost
payoff

```

`actual_capacity` 是抽样后四舍五入到两位小数的当轮正式服务率，同时用于结算、显示和已授权的 Agent 决策输入。审计记录应证明每个 Agent 决策时实际获得了哪些公开字段，但不得将 I0 不允许看到的容量回填到其决策输入快照中。

## 14. 迁移与兼容策略

- 不对已开始的事故版 Session 进行中途转换。
- 新逻辑只用于新建 Session；部署前完成或停止旧版实验。
- 事故版序列 JSON 不得被当作新均匀分布序列读取。新序列文件应使用新 `mechanism` 标识，例如 `uniform_stochastic_capacity_v1`。
- 对旧事故配置字段显式报错，而不是静默忽略或自动映射。
- 实现前必须检查当前工作树中未提交的事故 I0/I1 改动，不得回退与本次任务无关的用户改动。

## 15. 测试与验收清单

实现必须使用测试驱动方式，至少覆盖：

1. 正式配置只接受 `uniform` 且参数严格为 1.33 和 4.00。
2. 服务率序列长度等于当前正式轮数，所有值均为有限正数且位于 $[1.33,4.00]$。
3. 随机化分层生成器覆盖所有等概率层，同一种子生成完全相同的序列。
4. 序列 JSON 的机制、范围、轮号、种子和派生标签不一致时立即报错。
5. 同一 Session 的所有 Group 在同一正式轮读取相同 `actual_capacity`，但队列、选择和成本彼此独立。
6. I0 Human 决策页在提交前不显示数值、等级、颜色或图标暗示。
7. I1 Human 决策页在提交前显示与后端结算值完全一致的两位小数和正确等级。
8. I0 LLM 和 RL 决策输入不包含当轮容量或可逆派生量。
9. I1 Human、LLM 和 RL 获得相同的当轮服务率与等级。
10. I0 和 I1 在结算后获得相同范围的真实服务率和结果反馈。
11. 后端、Human、LLM 和 RL 对同一轮使用完全相同的两位小数服务率。
12. 同时到达瓶颈的主体继续使用相同批处理规则，面对相同队列延误和成本。
13. I0 RL 不使用当轮容量；I1 RL 的历史权重符合高斯核公式和冻结带宽。
14. I1 RL 历史稀疏时正确回退到 I0 历史，并在仍无法学习时使用预先冻结的探索规则。
15. LLM 调用失败时的备用策略不越过 I0/I1 信息边界。
16. 旧事故配置、序列和机制标识不能在新正式 Session 中静默运行。
17. H-I0、H-I1、HA-I0 和 HA-I1 四个正式配置均能正确创建。
18. 正式支付、导出、轮号映射和 RL 停止学习与实际正式轮数一致。
19. `single_bottleneck`、问卷和其他未改造 app 的回归测试通过。
20. 用 conda 中的 oTree 环境完成一次全轮次应用流程，确认 Session 创建、等待页、决策、Agent 选择、结算、结果和导出均可完成。

## 16. 实现顺序建议

1. 先为新均匀分布配置、序列生成和序列校验编写失败测试。
2. 实现独立的随机服务率模块，不在旧 `accident_capacity.py` 中继续叠加互斥概念。
3. 将 Group 当轮容量读取切换到新模块，先保证排队和成本回归测试通过。
4. 改造 I0/I1 公开上下文和防泄漏测试。
5. 改造 Human 页面、LLM 提示词和备用策略。
6. 用连续容量核替换 RL 的事故状态筛选，保留 Liu-REL 的其他核心逻辑。
7. 更新 Session 配置、自定义分组、导出和管理员报告。
8. 最后删除正式运行路径的事故字段和死代码，执行完整回归与全流程验收。

## 17. 非目标

- 不在本次改造中增加第三个信息组。
- 不增加带误差的容量预测。
- 不将精确容量改为只显示低/中/高标志。
- 不更改早到、迟到、排队、收费或支付公式。
- 不把均匀分布宣称为中国某条真实道路的实证拟合结果。
- 不使用正式实验结果调整分布、序列或 RL 参数，以追求预设方向的显著性。

## 18. 预期可检验关系

改造后的实验不保证某一结论成立，而是为以下关系提供可识别数据：

1. 出行前知道真实服务率是否提高主体对容量状态的反应程度。
2. 完全信息是否降低个体平均成本和成本波动。
3. 共同精确信息是否使出发时间集中，从而使系统总成本不降反升。
4. Human-Agent 混合系统相比全 Human 系统是否改变出发分布、系统成本和均衡收敛。
5. Agent 参与和出行前容量信息是否存在交互作用。

核心政策含义可被表述为一个待检验命题：

> 更准确的个体出行前容量信息可以改善个体决策，但当多个主体同时响应共同信号时，个体信息改善不必然转化为系统社会福利改善。
