# 每房间 40 人同步放行与决策计时设计

日期：2026-09-28。状态：用户已确认方案；本地协议实现与单元测试已完成，浏览器及 40/80 人负载验收尚未完成，正式开关保持关闭。

## 目标与证据

每个 Room 对应的 Session 独立运行。一个正式 Session 的 G01（H，30 Human）与 G02（HA，10 Human + 10 LLM + 10 RL）共 40 名 Human 应在同一轮收到同一个决策放行时刻和同一个 60 秒截止时刻；两个 Room 不互相等待。组内瓶颈、服务率、排队和结算仍各自独立。

目前 `RoundStartSync` 把“服务器处理了本组全部真人的 ready 请求”当作开始条件，立即设置该组 `decision_deadline_ts`。之后每人仍要经历准备页 GET/POST 和 Decision GET。2026-09-27 无干扰单房间 HTTP 测试中，33 人取得 Decision 页面时平均仅剩 11.59 秒，立即提交的 33 个请求也没有形成有效人工选择；双房间独立流程 80 人均没有形成有效人工选择。该证据证明现有流程不适合正式实验，但尚未定位单个最耗时函数，也不是 80 个浏览器的完整彩排。详见 `docs/准备页真人同步与决策计时_排查交接_2026-09-28.md` 和 `docs/双房间同步与生产验收报告_2026-09-27.md`。

## 方案比较

1. **只优化当前准备页并延后起表。** 修改少，但计时后仍有每人独立的 Decision GET 与 POST 排队，不能保证 40 人取得相同的可操作时间。不作为完整修复。
2. **每房间两阶段放行（推荐）。** 先让 40 名真人加载不可操作的决策壳页并确认；再按 Session + 内部轮次发出统一放行信号，公布允许的信息及选择控件，从共同放行时刻计 60 秒。真实缺席按已确认的最长等待与自动补选规则处理。需要一个可靠、经授权的轻量状态/推送通道，并验证请求截止判定。
3. **每人打开页后各计 60 秒。** 容易实现，但没有统一的同轮决策窗口，破坏用户要求。不采用。

仅增加 oTree WaitPage 也不够：WaitPage 可以使 40 人一起获准离开等待页，但其后的页面 GET 仍会排队。过去单瓶颈场景的“统一开始”设计不能直接作为本场景的并发验收证据。

## 每轮状态机

状态以 `(Session, 内部轮次)` 为键，保存在持久化的 Session/参与者状态中，不依赖单进程内存；两个 Room 的相同 P001–P040 标签绝不共用键。状态至少区分 `PREPARING`、`SHELL_LOADING`、`ARMED`、`RELEASED`、`CLOSED`，以及可识别的技术异常。重复 GET、ACK、POST 及进程重启不能重置阶段或截止时刻。当前部署保持一个 Web worker 和现有事务锁；若将来增加 worker，必须先重验跨进程原子性。

1. **准备。** 由本 Session 本轮第一个真人进入时创建准备截止时刻：内部第 1 轮最长 120 秒，其余轮次 60 秒。需等待名单来自此 Session 的 40 名真人，排除已有明确暂停状态者；LLM/RL 不参与到齐计数。准备阶段不启动决策时钟。
2. **加载。** 人工参与者获得决策壳页；静态 UI 和资源可以预载，但不能提交出发选择，也不能提前显示 I1 的本轮真实服务率。浏览器在页面实际可用后发送经身份校验、幂等的加载 ACK；仅服务器收到准备页 GET 不算加载成功。I0 在决定前始终不得获得本轮服务率。
3. **放行。** 全部需等待的真人 ACK 后，Session 为 G01/G02 原子地确定同一个未来放行时刻 `T`。客户端获知放行安排；只有到达 `T` 才显示决策控件及各条件允许的信息。两组共用 `T` 与 `T+60`，服务率和 Agent 记录继续按组独立。放行信号必须按参与者与 Session/轮次授权，不能靠隐藏按钮代替服务器校验。信号若到达迟缓，应记录每个参与者实际可操作的时刻；不能声称物理上完全同一毫秒显示。
4. **截止和结算。** 服务器拒绝 `T` 前或 `T+60` 后到达的人工提交；`T+60` 后不再接收新选择。有效人工提交的判定应使用**可信的服务器请求进入时刻**，而非客户端自报时间或因全局请求队列延迟后的业务处理时刻。截止前已进入但仍在锁队列中的提交属于待处理请求；不得抢先把这类参与者自动补选、结算或覆盖其人工决定。先处理这些待处理请求，再按现有规则补足真正缺失的选择；若队列无法在预设的有界清空期内完成，应将轮次标记为技术异常，而非静默丢掉合法提交。清空期只延后结果生成，不延长真人可提交的 60 秒。需先验证安装的 oTree 页面超时/自动跳页顺序以及请求进入时刻能否在事务锁前可靠传递；若框架先跳过页面，则不能仅在 `Decision.before_next_page` 补一个时间判断。提交来源、超时、自动补选与人工决策必须分别保留审计字段，原有成本、付费、RL 更新和导出语义不变。

## 未确认、迟到与技术异常

用户已同意沿用首轮 120 秒、后续 60 秒的准备最长等待。到准备截止仍未完成加载 ACK、且确属未到场/掉线的真人，不阻塞其余已确认者；按现有缺席/自动补选与恢复机制处理，明确记录为非人工选择。迟到者不能获得额外的个人 60 秒，也不能在放行后使 `T` 后移。

**服务器排队、推送失败或页面资源加载错误不能伪装成被试缺席。** 因系统原因导致未能 ACK/取得可操作页面的轮次应标记技术异常并从有效行为数据中剔除，供管理员处理；不自动把该人的选择重标为人工。诊断至少要能区分请求进入、业务处理、响应完成、页面加载 ACK 和实际可操作时刻。若现有准备最长等待内服务器排队频繁触发异常，必须先优化瓶颈并复测，不能用静默延长 60 秒决策窗口掩盖。

## 信息与数据边界

- I0 决策前仅能获得其允许的分布信息；I1 的本轮真实服务率仅在共同放行时刻及之后显示。不能把 I1 值预放在隐藏 HTML、脚本变量或未授权接口中。
- Agent 人格、RL 冻结预训练、服务率序列、30 轮正式实验、成本和奖励公式均不改变。可提前准备与本轮信息无关的静态资源；Agent 的实际本轮决策不得因预加载而改变既有信息集。
- H/HA 每组 30 个总主体及不同组的瓶颈结算继续保持。新的会话放行状态只协调真人计时，不合并两组队列，也不跨 I0/I1 Room 联动。
- 旧 Session 的进行中轮次不能被新状态机半途接管。发布时使用协议版本标记，让新建 Session 执行新规则，旧 Session 留在原规则直至结束；具体存储与迁移方案在实现计划中核验。

## 验证与上线门槛

先做无敏感内容的阶段耗时与 SQL/CPU 取样，确认锁前排队、锁内页面逻辑、Agent 准备各占多少。测试包括同 Session 40 人两组 ACK 顺序交错、另一 Session 独立启动、重复 ACK、页面刷新、掉线及恢复、缺席到准备截止、I0/I1 信息隔离、`T` 前后边界、截止前进入但锁后才处理的 POST、待处理请求未清空前的结果轮询、重复提交与结果幂等。有界清空期的具体阈值应由实测锁队列分布确定并经用户审阅；不能先拍一个数字充当实验计时规则。

使用隔离、明确标记的测试 Session：先单房间 40 人，再双房间各 40 人；先模拟 Agent 测流程，真实模型测试另行控制调用成本。除 HTTP 客户端外，必须用真实浏览器测试页面脚本、静态资源和实际显示时刻，并跑完 3 轮热身 + 30 轮正式实验。建议把“所有有效真人在 `T` 后 2 秒内得到可操作页面、服务端接受截止前进入的人工 POST、无异常自动补选”作为上线门槛；若负载下达不到，仍不能开展正式实验。记录并排除所有压力测试 Session，不将技术异常轮次作为研究样本。

方案阶段只改文档，不连接或重启服务器，不创建 Session、不运行付费 API，也不提交 Git。实现前由用户审阅放行时刻、缺席判定和上线门槛。
