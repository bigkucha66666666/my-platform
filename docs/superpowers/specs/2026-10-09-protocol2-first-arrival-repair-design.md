同一 Session 使用唯一 T 和 T+60；两个 Session 独立运行。重复请求、重连和刷新不能重新获得 60 秒。不以 T+2 秒或毫秒级显示同步作为本次完成门槛，也不通过延长决策窗口或相信客户端点击时间掩盖延迟。

本轮仅本地修改和隔离验证，不部署、不修改服务器数据、不调用付费 LLM、不自动 Git 提交。用户论文及其他无关工作区改动保持原样。

## 2. 已确认的规则及取舍

两种候选规则分别为“服务器首次收到完整合法请求”和“后台首次成功保存”。用户已选择前者。

这里的“收到”指控制端点读完请求体，并在服务器的短临界区内完成 JSON、签名身份、页面绑定和选择取值校验，登记待处理请求的时点。客户端时间、HTTP 建连时间和仅收到部分请求体的时间均不能决定选择。

同一 Session、轮次、参与者的合法 decision 请求按该登记顺序处理，再根据权威状态中的 T、T+60、ACK 和排除状态判断是否可作为 manual。早到、非法、未确认页面或其他不能成为有效 manual 的请求，不占用后续有效 manual 的最终值。

首次符合 manual 条件的请求决定最终值和服务器到达时间。相同服务器时间戳的请求以临界区内登记顺序打破平局。页面刷新得到的新 token 不应产生同一参与者的另一条独立排序通道。

只有持久化成功后才确认接收；后到请求在首次有效请求尚未处理完成时不能提前确认自己的值。已确认的 manual 不可被重试、不同值重放或原生表单覆盖。首次有效请求保存失败时，该轮进入技术异常，不以第二个值替代并认证为健康数据。

## 3. 修复设计

### 3.1 首次到达排序与持久化边界

在 `sync_transport.py` 与 `sync_runtime.py` 的既有完整请求体准入边界上，增加按 Session、轮次、参与者隔离的 decision 排序。

排序只负责调度先后，不作为持久选择的唯一事实来源。身份、轮次状态、最终回执和异常仍由独立日志决定。短临界区内不得进行 SQLite、oTree ORM、等待或线程池任务执行。

同一参与者后续 decision 在前序处理结束后才进入持久化阶段；不同参与者、不同 Session 的请求继续并行。不得让所有工作线程阻塞等待尚未运行的前序任务，避免线程池饥饿和死锁。排队请求计入现有有限准入和 pending 统计，不建立无界第二队列。

超时、客户端断开或 HTTP 响应取消，不能撤销已登记的服务器处理顺序。失败须保留现有故障联锁；结算关闭前必须清空待处理请求并检查联锁。排序记录在任务完成、轮次关闭及测试 runtime 重置时清理，不能无限积累。

### 3.2 原生表单必须消费权威回执

修改 `Decision.before_next_page` 与 `sync_integration.import_manual` 的协作方式，区分请求进入表单处理前已存在的选择和本次表单刚填入的字段。

若请求开始时没有既存选择，但回执在表单字段生成与校验之间落盘，即使 oTree 随后填入另一个出发值，也必须在推进前按权威 manual 回执重建出发值、时段、来源及相关人工选择记录。

不能因“当前 departure_minute 非空”就把本次未认证的表单填充值视为既存选择。已有结算结果、原有自动选择和真正既存的人工选择继续受到保护；旧协议行为不变。重复原生 POST 不重复改变缺席累计、恢复状态或选择来源。

### 3.3 前端决策发送不等待非决策请求

在 `room_release.js` 为 decision 设置独立的优先发送通道，不等待 status、ACK、operative 的在途请求或其重试退避计时器。

每个页面至多一个在途 decision，非决策请求仍合并并限制为一个在途请求。保存首次提交的选择，自动推进和重试不得改换该值。所有请求保留有界超时、时钟样本清理和技术异常停止逻辑。

响应确认仍以服务器持久回执为准，之后才调用原生表单推进。该设计只消除程序内部调度等待，不承诺消除客户端、网络或服务器的所有延迟。

### 3.4 当前轮次的原生页面故障不能认证为健康

修复 `decision_ingress.py`、`sync_runtime.py` 与 `sync_integration.py` 的故障关联和关闭边界。

Decision 原生请求在当轮未关闭时出现异常或 HTTP 500，必须关联到正确的 Session、轮次和页面，并阻止该轮健康 settled。判定不能只覆盖到 T+60；截止后到原生业务和控制关闭完成之前仍属于需要检查的故障区间。

故障登记与最终关闭应共享短同步边界，不能让“刚发生的故障”漏到关闭之后。不得在控制事件循环中为关联身份查询 ORM。真正已经关闭的历史页面重放失败不能反过来污染健康历史轮次；不同 Session、不同轮次的故障不得串扰。

### 3.5 技术异常仍保留已接纳请求的审计证据

请求在故障发生前已完成服务器准入，但尚未落盘时，即使业务清空守卫先标记队列超限，工作线程仍应尽力保存该请求的服务器到达时间、选择、身份及可判定的接收类型。

日志中的审计保留不等于健康接收确认；异常轮不能因后来保存成功而恢复健康，也不能进入正常成本结算认证。不能因此扩大 drain 时间、解除异常联锁或覆盖已经确认的 canonical manual。

故障发生后才到达的请求不得借审计通道获得新的健康 manual。日志本身不可用时，不回报成功，并保留现有故障联锁。未经落盘的 pending 不宣称具有断电后的持久审计保证；进程重启仍按现有异常规则处理。

### 3.6 普通迟到必须经过恢复确认

对于已确认的迟到请求，在原生 Decision 推进前建立必要的超时与恢复状态，让 oTree 的真实页面流程进入 RecoveryGate，而不是先进入 ResultsSync 才补标记。

有更早准时请求仍待处理时，不可提前分类为普通迟到、生成自动选择或让恢复状态覆盖后续 manual。必要时保留在 Decision 等待服务器确认。

自动补选与结果结算继续服从既有 pending、drain 和异常守卫；恢复页可显示“等待系统补选”，不能为展示自动时间而提前替换尚未清空的选择。

缺席计数每轮最多增加一次。参与者在 RecoveryGate 确认恢复后，后续 drain 补齐自动选择及策略审计不能再次激活同一次超时恢复标记，亦不能导致重复显示恢复页。原有已暂停参与者的代理选择与恢复分支保留。

## 4. 文件职责与变更边界

- `dynamic_bottleneck_round/sync_runtime.py`：有界排序与 pending 调度元数据、故障联锁、原生请求关联和原子关闭。
- `dynamic_bottleneck_round/sync_transport.py`：完整请求体准入、按参与者排序的持久化调度、响应及取消处理。
- `dynamic_bottleneck_round/sync_journal.py`：权威回执、异常时已接纳请求的审计保留；不增加业务 ORM 依赖。
- `dynamic_bottleneck_round/decision_ingress.py`：可信原生请求进入及完成观测、当前页面故障记录。
- `dynamic_bottleneck_round/sync_integration.py`：表单回执消费、结算前清空与故障检查、审计导出。
- `dynamic_bottleneck_round/__init__.py`：仅调整协议 2 Decision 与恢复/补选衔接，不重构无关实验业务。
- `_static/dynamic_bottleneck_round/room_release.js`：有界决策优先发送；不改页面布局。
- 对应 `test_sync_*`、`test_decision_ingress.py`、`test_room_sync_framework.py` 与 JS 测试：纳入可重复的失败回归。
- 新的本地验证记录及同步交接说明：写明首次规则、实际通过项和仍需服务器验证的边界；不改写原始报告与原始证据。

优先使用现有模块和日志结构，不引入 Redis、额外业务 worker、多主机同步或管理员逐轮启动按钮。

## 5. 验证策略和验收标准

先添加并观察失败，再做最小修复。临时 SQLite 和同步日志必须在独立临时目录创建，导入 oTree 前锁定数据库配置；不得读写项目或服务器业务数据库。

必须覆盖以下行为：

1. 真正的 oTree 5.11.5 GET/POST：回执在字段生成与表单校验之间落盘，最终业务值、来源与回执一致；既存自动/已结算选择不被覆盖。
2. 真实前端脚本的确定性测试：operative 响应挂起或处于退避时，第 59 秒提交立即启动 decision 请求；不等待十秒超时，不延长窗口。
3. 第一份合法准时请求先登记但处理暂停，第二份后登记且可运行时，不提前确认第二个值；释放第一份后两者返回同一 canonical。该测试须同时运行两请求，再释放阻塞，不能用“等待第二份先返回才释放第一份”制造测试自身死锁。
4. 更早非法/早到请求不抢占有效值、不同 token 不绕过排序、同时间戳按登记顺序、重试与取消不覆盖、首次保存失败不健康降级；不同参与者和两个 Session 独立。
5. 截止后但当前轮关闭前的原生 Decision 500 阻止健康 settled；历史已关闭页面重放失败不污染新轮或已完成轮。
6. 故障前准入、故障后才执行的请求保留审计，仍为技术异常；故障之后的新请求不能获健康确认。
7. 真正迟到者经原生 POST 进入 RecoveryGate，恢复后正常等待结果；pending manual 不被提前补选，同轮缺席及恢复状态幂等。

修复后运行协议 2 相关单元、原生框架和 JS 回归，并检查旧协议、Room、分组、I0/I1 隐私、暂停代理与支付流程。低资源验证一个 40 人和两个 40 人 Session 的准时接收、截止突发和隔离；完整 33 轮验证继续使用真实 RL 与模拟外部付费 LLM。

不集中启动 80 个 Chrome，不重复保留后台服务。测试子进程和本轮创建的资源及时退出；每次只能启动一套所需测试服务。

服务器隔离 PostgreSQL、校园网络和少量实际浏览器的原入口至结束验收属于后续上线步骤；本地自动测试通过不得写成已经部署或保证任何网络条件下绝对同时。
