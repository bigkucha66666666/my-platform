# 准备页真人同步与决策计时：排查交接

日期：2026-09-28。本文只梳理现有代码和 2026-09-27 的部署验收证据；未修改代码，也未重新连接服务器验证实时状态。

## 先澄清同步语义

- `round_waiting_players(group)` 使用 `group.get_players()`，排除已暂停掉线的参与者。虚拟 LLM/RL Agent 不计入准备页的到齐人数。同步范围是**每个瓶颈组**，不是一个 Session 的全部 40 名真人，更不是两个房间的 80 名真人。正式配置中，每个房间 G01 为 30 名真人，G02 为 10 名真人及另外存储的虚拟 Agent。
- `RoundStartSync.is_displayed` 调用 `mark_round_ready`。当本组需等待的真人全部被服务器标记为 ready，`maybe_start_round` 立即设置 `round_started_at_ts`，并设置整个组共用的 `decision_deadline_ts = effective_start_ts + 60 秒`。
- 这不是无条件“必须等齐”：若未到齐，准备页等待截止后也会启动。首轮最长等待 120 秒，后续轮次 60 秒。超时启动时 `effective_start_ts` 取原准备页截止时刻；如果请求实际处理晚于该时刻，决策时间可能在页面响应前已消耗一部分。
- 到齐只意味着**服务器已收到本组每人的准备页请求**，不意味着每个人已收到“本轮开始”响应、已离开准备页、已拿到 Decision 页面，或其提交请求已经被服务器接受。

## 为什么仍可能有请求排队

时间线是：最后一名真人的 ready 请求在服务器完成判定时记为 T0；该组决策截止为 T0+60 秒。其他真人还要继续完成准备页轮询 GET、自动继续 POST、Decision GET、人工 Decision POST。准备页脚本未就绪时错峰刷新，就绪后约 200ms 自动继续。上述请求都是独立的 HTTP/数据库工作，即使只等待真人，也不会因为同步条件满足而瞬时完成。

`Decision.get_timeout_seconds` 使用组级剩余时间，而非从各人打开 Decision 页起重新给 60 秒。`Decision.error_message` 和 `before_next_page` 都会检查组级截止时刻。若 POST 在截止后才被处理，点击按钮的时间早于截止也可能无法保存为人工选择。`Decision.is_displayed` 还会触发 Agent 预取、RL 准备和结果就绪检查；这些调用是否是主要耗时来源，现有证据**尚不能确定**。

## 已有验收证据

- 2026-09-27 的单房间 40 人独立 HTTP 客户端复测：7 人拿到 Decision 前已被跳过；33 人拿到 Decision 时仅剩 1.79–20.98 秒，平均约 11.59 秒。33 人随后立即发出 POST，平均耗时约 17.26 秒、P95 约 25.11 秒，没有一个被核验为有效人工选择。
- 同次双房间 80 人准备到决策流程复测：80 人均未完成有效人工选择，后续结果虽被自动补选结算，不能作为合格真人决策数据。
- 跳过准备页、直接把人放在 Decision 的专项测试可以完成 80 人提交及结果复算，但不覆盖准备页到决策页的时间损失，因此不能用来否定上述完整流程失败。
- 测试使用服务器本机的独立 HTTP 客户端，不是 40/80 个真实浏览器；未包含页面静态资源、校园网延迟、理解题及 33 轮完整操作。它证明存在负载风险，不代表真实实验必定出现同样比例的超时。

详细数字和测试边界见《双房间同步与生产验收报告_2026-09-27.md》，原始记录见 `output/dual80_20260927/20260927_single40_i0/report.json` 与 `output/dual80_20260927/20260927_dual80_flow_clean/report.json`。

## 尚未定位的根因

现有结果能说明**等待到齐之后的请求处理与页面推进吞掉了组级决策窗口**，但不能确定耗时主要来自 oTree 请求事务、数据库查询、重复轮询、Agent/RL 准备、服务进程调度或其组合。不要在没有分段计时证据时断言“Agent 没准备好”或“某个锁是唯一原因”。另外应核验失败轮次是“全部真人到齐启动”还是“准备页截止后启动”，两者都会产生相似表象，但修复点不同。

## 本地修改与复测建议

1. 先加入低开销、无敏感信息的分段计时：每组的 ready 人数、启动原因、`round_started_at_ts`、决策截止时刻；准备页 GET/POST、Decision GET/POST 的请求进入、关键函数耗时、响应完成；Decision 页实际渲染时剩余秒数与 POST 被接受/拒绝的原因。若能在请求入口与应用处理之间区分等待时间，优先保留该指标。
2. 明确产品语义：实验设计是“最后一人标记 ready 后统一计时”，还是“所有需要决策的真人都已收到 Decision 页面后统一计时”。目前实现是前者。若要改为后者，应先设计两阶段确认机制并评估对统一时钟、公平性和掉线处理的影响，不要只给每个人重置 60 秒。
3. 在定位瓶颈后，只针对被证实的关键路径优化，例如减少准备页重复查询、将安全的准备工作移出决策计时关键路径或使用轻量同步状态接口。不要盲目增加 worker、绕过事务锁或静默延长实验计时。
4. 先复测一个房间 40 人，再同时复测两个房间各 40 人。验收需同时看：Decision 页面剩余时间、截止前立即提交的接受率、人工/自动选择来源、H/HA 与 I0/I1 结算一致性、重复结果读取幂等性；最后进行 33 轮真实浏览器彩排。
