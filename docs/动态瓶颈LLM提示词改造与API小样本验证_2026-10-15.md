# 动态瓶颈 LLM 提示词改造与 API 小样本验证

日期：2026-10-15。范围：仅 `dynamic_bottleneck_round` 的 LLM；本地代码改动，不代表已同步服务器。

## 改动与不变项

新版 `dynamic_bottleneck_prompt_v2` 完整重写系统与用户指令，用中文区分时间规则、客观成本、信息条件、历史反馈、人格、受限记忆和最终 JSON 输出。

到达时刻按“出发 + 固定行程 + 非负额外瓶颈行程”理解，瓶颈通过时间全部计入额外行程；早晚到围绕目标时刻计算，成本系数从请求的 `cost_parameters` 读取。当前场景没有额外收费或奖励，不改变生产结算。

每个合法档位新增 `fixed_travel_arrival_minute` 和 `fixed_travel_arrival_time`：仅计算“出发 + 固定行程”的到达下界，不预测排队、不估计总成本、不筛掉晚到档位。当前固定行程 6 分钟时，07:54、07:57、07:59 分别得到 08:00、08:03、08:05；更换固定行程参数后参照随之变化。

明确 I0 选择时不知道当轮实际服务率，I1 仅可使用已公开的值；两者都看不到其他主体当轮选择及未来序列。历史空档成本未知，不是零；历史服务率不是本轮已知服务率。记忆只是可修正印象，不能把尚未结算的选择或预测写成已发生事实。

要求 `reason` 简短且与最终档位、时刻相符，启用记忆时返回有界 `memory_summary`。不增加语义解析器、重试或强制最优覆盖。正常但高成本的合法行动仍由 Agent 自主选择。

保持人格、RL、队列与成本、30 轮正式实验、热身隔离、问卷和报酬不变；不改变 API 模型、温度、thinking、输出预算、timeout 和原有错误回退。

## 版本与启用

新建动态场景 Session 的配置保存 `api_agent_prompt_version=dynamic_bottleneck_prompt_v2`。缺少该配置字段的旧 Session 继续使用原始 `dynamic_bottleneck_prompt_v1`；旧版消息已做改造前快照核对。非法版本在创建时明确拒绝。

因此，同步代码并按既有方式重启应用后，需**新建 Session** 使用新版，不要为切换提示词中途修改正在运行的 Session。本次没有部署或重启线上服务，也没有 Git 提交。

新产生的 LLM 决策记录保存 `prompt_version`，模型/策略标识仍单独保存。正式长表和“导出本 Session 全部轮次”均新增 `agent_prompt_version`。旧记录没有该字段时导出为空，不依据今天的默认值回填；Human 和 RL 为空。v2 的 `agent_context_json` 记录模型实际收到的派生上下文，便于核对时间参照。

这些字段保存在既有配置与记录字典中，无需数据库结构迁移。后续若再次改变 v2 指令语义，应提升版本号，不能继续沿用 v2 标签而静默修改。

## 真实 API 小样本设计

用户追加授权后，仅进行一次 **3 个模拟轮次 × v1/v2，共最多 6 次请求**，无重试，不读写现有 Session，不读取 S01–S05 或 RL 训练经验。脚本：`scripts/check_dynamic_llm_prompt.py`，重复使用时必须另行确认调用预算；本次调用额度不是长期监控授权。

固定独立种子 `2026101501`，29 个外部主体用独立模拟策略选择，1 个席位调用 LLM，总计 30 个主体。两版共享外部行动和当轮模拟服务率，分别保留各自上一轮公开反馈、个人结果与受限记忆。使用 `adaptive_v1` 同一人格、I0 信息条件；当轮服务率不进入请求，结算后才进入下一轮历史。结算复用生产纯计算函数，并与现有独立市场模拟器逐项比对成本。

这不是两组完整真人市场或 10 个 LLM 同时竞技，也不是严格的逐轮固定历史对照：首轮历史相同，之后两版因自身行动不同，个人结果和公开反馈可不同。换档次数、成本和延迟只作本次描述，不能证明长期稳定或推断正式实验处理效应。

为防误触，真实调用必须显式传入 `--real-api`；输出路径必须为新文件，不覆盖既有报告。凭据只读取现有配置，不序列化到报告。每次调用后保存进度，以免中断后误把已发生调用当成未调用。

## 本次真实结果

报告保存在 [独立模拟调用原始记录](../output/llm_prompt_20261015/api_comparison.json)。实际使用既有配置：`deepseek-v4-flash`、temperature `0`、thinking 关闭、max_tokens `512`、timeout `12` 秒、受限记忆开启且上限 `400` 字符；未输出密钥。

共尝试 6 次 HTTP 请求，两版各 3 次，**全部返回 `The read operation timed out`，成功获得模型回答 0 次**。实际耗时 12,261–12,423 ms；这里是失败请求到超时的耗时，不能解释为成功响应延迟。没有重试、补测或调整生产 timeout。

因此这次无法评价时间换算、理由与档位、记忆内容有没有好转，也无法确认服务端是否已处理或计费。没有收到模型响应，不能据此判断模型名称、额度或提示词长短是原因；尤其原版同样超时，不能把问题归因于新版提示词。

两版记录中的 `[9, 9, 9]` 均由既有 `fallback_lowest_schedule_cost` 产生，平均模拟成本 `18.8579` 也是这些回退行动的结算值，**不是 LLM 的回答、学习稳定性或新版改进证据**。原始 JSON 为透明审计保留了这些回退记录，不得将其混入正常 LLM 行为比较。

当前可确认的是代码、旧版兼容与离线契约通过；真实回答质量仍未验证。后续若重新测试，应在网络或接口状态恢复后另行确定调用预算、保留当前版本，并明确是否沿用同一个 12 秒部署超时。不能根据本次正式结果调参，本次也没有追加调用。
