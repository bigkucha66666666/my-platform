## 1. 本次目标与规则

按照[原问题报告](/Users/hybsmac/Python项目/economics-experiment/my_platform/docs/协议2对比评估与预实验建议_2026-10-09.md)及用户选择的方案 1，修复同步机制的六项缺口，不删减实验流程。

“首次选择”现在按**服务器完成合法请求体校验并登记的顺序**确定，不按工作线程先后提交 SQLite 的顺序确定，也不相信客户端点击时间。按 Session、轮次、参与者串行处理 decision；刷新产生的新 token 不能绕过同人的顺序。早到或其他不符合 manual 条件的请求不抢占后来有效选择。

只有持久化成功才确认接收。首次有效保存失败时，进入技术异常，不采用后到的另一个值作为健康替代。HTTP 响应丢失或客户端取消后，已准入工作仍完成；重试返回原有 canonical 回执，不改第一次有效值。

每个 Session 仍只有一个开始时间 T、一个截止时间 T+60；两个 Session 各自独立。不承诺所有设备同一毫秒显示，也不承诺任意网络延迟都能消除。

## 2. 六项修复与额外边界

| 原问题 | 当前处理 |
| --- | --- |
| 回执474、原生表单475，来源为空 | 原生 POST 明确记录表单填值前是否已有选择。仅本次新表单值可被 canonical manual 校正；保护原有自动选择、人工选择与已结算结果。 |
| operative 挂起阻挡 T+59 decision | decision 与 ACK/status/operative 分成独立有界通道，每通道最多一个在途请求；decision 不等待非决策响应或退避。首次选择保留，原生推进最多一次。 |
| 后到请求先提交，抢占最终值 | 按同人服务器登记顺序调度，只有队首进入持久化；不同人和不同 Session 仍可并行。后继不占用线程等待前驱，排队计入既有有限准入。 |
| 截止后原生500仍可健康关闭 | 业务验证后绑定参与者/页面到轮次，原生请求完成前仍持有 pending；故障先联锁再释放，关闭使用同一同步边界。正常在途请求安全延后关闭，已关闭历史重放不污染历史轮。 |
| 故障前已准入请求丢失审计 | 保存独立 admitted_decision 审计。权限由服务器内部 ticket 与故障序号边界授予，JSON不能伪造；它不是健康回执，不解除异常，不进入人工选择或成本计算。 |
| 普通迟到跳过RecoveryGate | 原生推进前激活当轮超时/恢复，实际进入恢复页。确认恢复后的补选只补策略审计，不重复激活恢复或增加缺席计数；pending manual不提前补选。 |

独立补查还修复了“字段选定后才被排除”的竞态：本次原为空的表单，即使 validation 期间才发生 exclusion，也不能留下未经 canonical manual 确认的出发值；后续按现有缺席补选规则处理。该用例先在真实 oTree 框架中断言失败，再修复通过。

前端技术停止后迟到的 decision HTTP400 不再创建新的诊断等待计时器；既有有限请求超时与清理保留。

最终审查还补齐首份请求自身执行失败的审计：先建立并持久化故障联锁，再在首份ticket仍有效时尽力保留其证据，然后才释放并调度后继。后份排队值不能替代首份故障审计；若审计也失败，保留原执行异常和故障联锁，不回报健康成功。两项新增断言先真实失败，补修后进行局部覆盖。

## 3. 数据与导出

canonical `receipt` 仍是人工选择的唯一权威。新增五列仅用于故障调查：

- `room_release_admitted_kind`
- `room_release_admitted_departure_minute`
- `room_release_admitted_ingress_ts`
- `room_release_admitted_shell_token`
- `room_release_admitted_page_index`

其中 kind 为忽略技术异常后按当时状态可判定的 manual/late/excluded；departure_minute 保留原始请求值，即使 kind 为 late/excluded 也不是用于计算成本的补选值。这些列不对控制端点暴露，不作为行为结果输入。技术异常仍标注 `room_release_exclude_behavior`；旧协议、未开始的未来轮和虚拟Agent对应列为空。

日志不可用、进程崩溃或断电时不能保证尚未落盘的 pending 审计；未完成轮次重启继续按既有技术异常保护处理，不宣称 RAM 登记具有持久保证。
