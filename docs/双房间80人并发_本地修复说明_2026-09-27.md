# 双房间 80 人并发：本地修复说明

日期：2026-09-27。依据《60人并发压力测试与修复建议_2026-09-27.md》修改。本说明记录本地实现和回归证据，不是生产环境 80 人并发验收报告。

## 已修改

1. **纯 Human 小组不再永久等待 LLM。** Session 级 `api_agent_mode=active` 只表示某个小组需要 LLM，不代表所有组都有 LLM。启动、收集和同步兼容入口现在先检查当前组人数；零 LLM 返回 None/[]，不进入共享缓存、抢锁或请求线程池。无 RL 的小组同样跳过记录查询、状态和预训练准备。
2. **已结算组立即返回。** `maybe_prepare_results` 在入口检查 `results_ready`，结果页与等待页重复读取不再执行启动检查及暂停参与者补选。
3. **准备页复用等待人数查询。** `mark_round_ready` 已进行启动检查，渲染不再重复调用启动函数；已到齐人数和组人数共用一次等待参与者列表。
4. **结果页共用当前轮公共快照。** 出发分布和成本图使用结算时保存的匿名 `departure_outcomes`，一份快照同时用于两张图，不重查虚拟主体记录。旧 Session 没有快照时保留计算回退；不新增数据库字段或跨 Session 的全局结果缓存。
5. **同步页错峰退避。** 两页共用 `_static/dynamic_bottleneck_round/sync_poll.js`。未就绪时最初计划等待 1500–1999ms，再按 1.35 倍退避，基础等待上限 3500ms 加 0–499ms 随机偏移；就绪仍按原有 200ms 前进。计数按参与者页面路径和页面类型隔离，就绪清除，浏览器禁用存储也能继续刷新。此上限只是客户端设定的等待时间，不含请求排队、网络或浏览器后台节流。

## 保持不变

- 两个 Rooms 对应两个独立 Session；每个 Session 40 Human，标签前 30 人 H，后 10 人 HA；HA 另含 10 LLM 和 10 RL。
- 原有 oTree 请求事务锁与按 Session/组/轮次的结算锁。
- 3 轮热身、30 轮正式实验、60 秒统一决策窗口、50 秒结果页。
- 服务率序列、截断正态参数、I0/I1 信息范围、成本、付费与 RL 预训练/在线更新规则。
- 数据导出格式。快照来自已结算结果，没有向 I0 决策页新增当前服务率。

新增性能回归约束：有结算快照的 Results 渲染路径只获取一次组参与者列表。对同一假组分别执行 HEAD 的旧函数和修改后函数，`group.get_players()` 调用由 **5 次降至 1 次**。这不是完整 HTTP 请求的 SQL 数量，也不代表请求时间按比例下降。

完整工作树中的论文编译日志存在既有尾空格；未修改这些无关文件。未部署、未重启服务器、未修改数据库结构、未提交 Git。

以后同步服务器时，必须一并同步动态场景 Python 文件、两个同步页模板和新增的 `_static/dynamic_bottleneck_round/sync_poll.js`，不能只复制后端文件。新静态文件缺失会导致模板渲染或自动刷新失败。

## 正式实验前仍需验收

这些修改消除了确定的功能阻塞并减少重复工作，**尚不能证明生产服务器能稳定承载 80 人完整实验**。

后续应在明确标记、独立于正式数据的测试环境同时运行 I0/I1 两个 Session，测试 80 个完整浏览器、全部 33 轮、两种信息条件及 H/HA，包含登录标签、页面 JavaScript、超时/恢复、最终问卷与结算。先用模拟 Agent 覆盖流程；真实模型测试另行控制调用成本。

重点记录准备页、决策页及提交的平均/P95/最大耗时、进入决策时剩余秒数、超时补选比例、LLM/RL 记录完整性和重复结算一致性。用每请求 SQL/CPU 耗时定位剩余串行开销；再决定是否需要轻量状态接口或部署调整，不直接绕过事务锁或增加 Web worker。

本次只增加时限边界回归，没有改变“按服务器处理时刻判断截止”的规则。如果负载复测仍发现截止前发出的请求因排队被拒绝，需单独确认请求到达时间口径并进行部署层验证；不要静默延长实验窗口或事后将补选伪装为人工选择。
