## 准备到决策流程：未通过

这部分不再直接将参与者放到 Decision。客户端从 RoundStartSync 开始，各自按未就绪时错峰退避、就绪后约 200ms 前进的方式推进；进入 Decision 后立即提交预设选择。没有统一等所有人完成上一阶段再开始下一阶段。保持原有准备、决策及结果时限。

这是独立 HTTP 客户端流程，不是 80 个浏览器；不加载图表资源、页面 JavaScript、WebSocket 自动推进或校园网延迟。结果只能用于压力风险判断，不能推断真实被试必然按同一比例超时。

## 工具错误与证据边界

1. 最初服务器回归的两个测试因 Node v10 不支持 `node:assert/strict` 失败。生产文件当时尚未切换；改用项目隔离的新版 Node 后，所有测试通过。
2. 最初房间入口检查只接受 302，而 oTree 实际返回合法 307。已修正测试工具；没有修改生产重定向逻辑。
3. 早期轮次 8 的观察函数误调用 `active_virtual_decisions_for_group`，可能更新掉线状态，并与超时进程竞争事务；出现一个 500。该轮不作为无干扰验收结论，异常不简单归咎于生产逻辑。诊断改为纯 SQL 后在新轮次 11 重测，仍证实严重排队和全部自动选择，但没有 500。
4. 并发脚本没有运行完整 33 轮浏览器实验，也没有完成登录、理解题、最终问卷、恢复重连的全链路压力验证。问卷等有单元回归证据，不等于多人端到端验收。
5. 测试都在服务器本机访问 18000。端口 80 属于其他项目，未使用或修改其代理配置。

## 后续处理建议

优先对 RoundStartSync GET/POST、Decision GET/POST 进行每请求 SQL 数量、耗时及 CPU 采样，定位仍然重复的参与者/Agent/掉线状态查询和预备工作。在确认 oTree 的事务和跨进程状态一致性后，考虑轻量状态轮询接口、减少组级重复工作、将可安全预计算的数据移出请求关键路径。

没有充分证据支持直接绕过事务锁或盲目增加 worker；不应静默延长 60 秒窗口，也不应将自动选择重标为人工选择。优化后先复测单房间 40 人，再测双房间 80 人；合格标准应包含足够的实际决策剩余时间、截止前提交被接受、无异常自动选择、数据复算一致。最后再进行完整 33 轮真实浏览器彩排。
