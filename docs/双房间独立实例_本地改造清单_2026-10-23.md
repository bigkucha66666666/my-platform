# 双房间独立实例：本地改造清单

日期：2026-10-23。本文供本地修改和后续验收使用；尚未实现双实例，也未据此修改线上服务。

## 1. 先改什么

目标是让 I0、I1 两个房间的业务请求分别排队，减少两个房间互相阻塞。建议先完成两个本地端口的隔离运行，再处理同一个公网 IP、Nginx 80 端口的统一入口。

当前两个 Rooms 已经对应两个独立 Session，但仍在同一个 oTree 业务进程内处理请求。仅在后台创建两个 Rooms，或者给同一个应用增加两个监听端口，都不能拆开这一队列。

建议本地结构：

```text
I0 本地入口 127.0.0.1:8001 → oTree 实例 I0 → I0 数据库、同步记录、超时进程
I1 本地入口 127.0.0.1:8002 → oTree 实例 I1 → I1 数据库、同步记录、超时进程
```

每个实例继续使用一个 Web worker。两个实例可以使用相同版本源码和同一个 Python 环境，但运行目录、数据库与可写状态分别独立。

## 2. 第一批：实例启动与状态隔离

### 2.1 新增实例启动配置和启动入口

建议新增 `instance_config.py` 与 `run_instance.py`，分别负责配置校验、加载配置后启动既有 `project_prodserver.main()`。这两个文件目前不存在，属于建议新增内容。

启动配置必须在导入 oTree、项目 settings、数据库和 Agent 模块之前生效。当前 `project_prodserver.py` 在模块顶层导入 oTree，因此不能先导入它、再覆盖数据库变量。

| 配置项 | I0 实例 | I1 实例 |
| --- | --- | --- |
| 实例标识（建议新增配置） | `i0` | `i1` |
| 本地监听地址 | `127.0.0.1:8001` | `127.0.0.1:8002` |
| `DATABASE_URL` | 独立测试 PostgreSQL 数据库 I0 | 独立测试 PostgreSQL 数据库 I1 |
| `DYNAMIC_ROOM_SYNC_DB` | I0 状态目录下的绝对路径 | I1 状态目录下的绝对路径 |
| 运行目录及 `db.sqlite3` | I0 独立目录/文件 | I1 独立目录/文件 |
| `TMPDIR` | I0 私有临时目录 | I1 私有临时目录 |
| `OTREE_SECRET_KEY` | I0 独立值 | I1 独立值 |
| 超时进程 | I0 主进程自己的子进程 | I1 主进程自己的子进程 |

配置文件放在本地私有目录，版本库只保留不含密码的示例。实例模式缺少数据库、状态目录或实例标识时应拒绝启动，不能静默继承项目 `.env` 的数据库地址。`settings.py` 目前会读取项目 `.env`，因此必须专门覆盖并验证这一行为。

建议由启动工具生成两份固定版本的本地运行副本，分别切换工作目录后启动；复制时排除 `.env`、数据库、Git 和历史输出，保留运行所需的源码、模板、静态资源及标签文件。源码修改仍只在主项目中进行，再重新生成运行副本。不要让两个进程在同一个项目工作目录下创建或使用同一份 `db.sqlite3`。

两个配置必须在启动前一起校验：数据库目标、journal 路径、运行目录、临时目录和端口均不能相同。对路径做绝对路径及符号链接解析，避免两个不同写法最终指向同一文件。

### 2.2 需要核对的现有文件

| 文件 | 本地工作 |
| --- | --- |
| `project_prodserver.py` | 复用当前单 worker 启动方式及父子进程秘密传递；从已验证的实例环境启动 |
| `project_timeout_worker.py`、`timeout_navigation.py` | 验证超时子进程继承本实例配置，直接请求本实例端口，签名不能跨实例使用 |
| `dynamic_bottleneck_round/sync_runtime.py` | 验证显式 journal 路径生效；两个实例不能共用 journal |
| `dynamic_bottleneck_round/agents/prefetch_coordinator.py` | 目前按系统临时目录和 UID 保存预取锁/结果；使用各实例独立 `TMPDIR`，并验证实际缓存路径不同 |
| `settings.py` | 增加实例模式配置入口，防止回落到原 `.env`；保留原单实例启动方式 |

不同 PostgreSQL 数据库可以放在同一 PostgreSQL 服务中，不要求安装两套 PostgreSQL。不能仅使用同库的不同 Session 来代替数据库隔离：当前超时任务队列没有按房间消费的隔离条件。

同步 journal 也不能共享。当前 journal 记录进程启动身份；两个独立进程共享它，可能把对方尚未结算的轮次识别为重启异常。Agent 预取缓存则需要在同一实例的 Web/超时进程之间共享，在不同实例之间隔离，继续保留防重复调用的文件锁和已开始标记。

## 3. 第二批：每个实例固定一个实验条件

涉及 `settings.py`、`_templates/otree/includes/DynamicSessionControls.html`，以及 `dynamic_bottleneck_round/__init__.py` 的创建 Session 校验。

- I0 实例展示 `prod_room_i0`，默认 `PAIR-I0`；I1 实例展示 `prod_room_i1`，默认 `PAIR-I1`。
- 服务端校验新建 Session 的房间、组别和信息条件与实例一致。只隐藏另一选项或修改前端默认值不够。
- 每个房间仍为 40 名真人：P001–P030 为 H，P031–P040 为 HA；HA 另有 10 LLM 和 10 RL。
- 可以继续复用 `_rooms/econ101.txt`。不同数据库中的相同标签不代表同一参与者身份。
- 对比实验仍要给两个 Session 选择相同的冻结服务率序列，例如同一个 S01–S05；拆实例不会自动保证序列相同，也不建立跨房间轮次屏障。

旧单实例模式应继续可启动；不重写历史 Session。双实例先使用新建的独立测试库和明确标记的测试 Session。

## 4. 第三批：统一 Nginx 80 入口

这一部分放在两个本地实例通过后实施。最终公网仍可保持 Nginx 80，两个应用端口只监听本机。

当前没有域名，不能把“两个域名分别代理两个实例”直接当作现成方案。若采用同一 IP 下的 `/i0/`、`/i1/` 路径，需要先验证项目和 oTree 的完整路径前缀支持，再编写代理配置。

必须覆盖以下请求，并保证一个浏览器身份始终进入原实例：

- 房间入口、登录、`/p/...` 参与者页面、表单提交和重定向。
- `/dynamic-room-sync` 控制请求、`/live` 与 `/auto_advance` 等 WebSocket。
- 管理后台、创建 Session、REST 接口和数据导出。
- 静态资源地址，以及登录/会话/CSRF 等实际使用的 Cookie 范围。

不能只按 `/room/prod_room_i0` 和 `/room/prod_room_i1` 转发：进入参与者页面以后，路径本身不再包含房间名。也不能对两个实例做普通轮询负载均衡。仅设置 ASGI `root_path` 是否足够尚未验证，项目存在绝对路径，不能据此直接上线。

两个实例使用不同签名密钥时，还必须隔离同一 IP 下的 Cookie；端口号不能隔离 Cookie。本地初步测试可以先使用两个独立浏览器配置文件，避免登录状态互相覆盖；同一浏览器、统一入口的验收仍须单独完成。

## 5. 本地验收顺序

1. **启动隔离检查**：配置缺失、端口重复、同库、同 journal、同临时目录均拒绝；两个实例能同时启动，Web 和超时子进程使用对应数据库与端口。
2. **串场检查**：I0 的参与者、控制令牌、超时签名和管理会话不能在 I1 上使用；反向同样验证。两个实例即使出现相同测试 Session/参与者 code，也不能共享状态或缓存。
3. **故障隔离检查**：仅在测试环境拖慢或停止 I0，I1 能继续处理请求，journal 不因另一实例启动而产生故障；同一实例真正重启时，原有保护继续生效。两个实例仍共享主机资源，因此不能承诺数据库或整机故障互不影响。
4. **分项计时**：分别记录请求排队、进入业务处理后的耗时、H/HA 结算、结果页渲染、下一轮页面加载、房间等待就绪和放行倒计时。只记录匿名计时及计数，不把完整参与者内容写入性能日志。
5. **完整流程回归**：两个实例同时运行，每实例 40 真人席位，全部 33 轮，覆盖 2640 次人工选择、80 人问卷、排名、正式成本与最终报酬审计。先模拟付费 LLM，实际调用另行授权。
6. **统一入口浏览器验收**：经过本地代理模拟最终 80 端口路由，覆盖 I0/I1、WebSocket、超时自动推进、刷新重连、两个后台同时登录和导出。通过后再安排 ECS 切换。

性能比较应使用相同机器、版本、数据和负载，报告 P50/P95/最大值及异常数量。现有 80 人测试中 `GET ResultsSync` 的最大 13.34 秒包含请求排队；并未测得单独计算一个 30 主体小组需要 13.34 秒，也不能承诺拆实例后耗时减半。

## 6. 此次不需要先改的实验逻辑

- 不把 oTree 当前原生事务锁直接替换成“按房间加锁”，不在同一个应用实例内直接增加 Web workers。
- 不改变每个房间 H/HA 独立结算及当前房间内两组结果都就绪后进入结果页的条件。
- 不缩短或绕过准备、ACK、截止、drain、异常保护；新 Session 的 3 秒放行及旧 Session 的版本兼容继续保留。
- 不修改决策时长、成本、排名、奖励、Agent 策略和 3 轮热身加 30 轮正式实验。

拆实例解决两个房间共用业务请求队列的问题；同房间等待另一组、Agent 工作、单组结算和固定放行时间仍然存在。应依据分项计时决定是否继续优化同步查询，而不是先放宽同步判定。
