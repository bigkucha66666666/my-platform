## 仍需解决的验收点

40 人首轮浏览器提交到下一页的耗时中位数约 9.10 秒，P95 约 11.97 秒，最大约 12.08 秒。没有拒绝决定，但并非即时响应。

80 人已结算组的服务器可信时间戳：锁前到达到业务处理，1150 个样本，中位数约 5.57 秒、P95 约 18.87 秒、最大约 23.78 秒；已持久化的到达至响应完成时间有 1125 个样本，最大约 23.88 秒。缺失完成时间的样本不能按零等待处理。

浏览器以 WebSocket 回显对应请求、服务器采样时间和本地单调时钟估计实际可操作时刻，得到的是含网络与队列误差的区间，不是浏览器墙钟与服务器墙钟直接相减。1200 次页面操作记录中，估计下界最大约 T+19.32 秒，上界最大约 T+25.23 秒；该测试环境不满足设计中的 T+2 秒可操作目标。

本地 16 GiB 测试机集中运行 80 个独立浏览器，自动 Chrome 进程 RSS 汇总采样约 18.9 GiB，存在客户端资源压力。不能据此断言 80 台真实参与者设备会有相同时差。另一方面，服务器锁前入口到处理的排队时间是独立测量，不能全部用本地浏览器过载解释。服务器资源记录只是采样，并非完整峰值监控。

隔离测试的清空期为 10 秒。实测排队超过 20 秒意味着：如果有效 POST 在截止前集中到达，可能在截止后的清空期结束前无法完成，从而触发 `decision_post_queue_overrun`。本次多数客户端放行后即提交；没有据此声称已经发生截止前提交丢失，也没有声称 10 秒配置已通过截止突发测试。

`operative_ts` 的服务器留存只有部分记录，不能当成全体客户端的可操作时刻证明。应进一步核查快速 POST 与 operative 回执到达顺序下的审计完整性。

## 本地交接与后续启用

1. 先分别复测单房间 40 人与双房间 80 人。浏览器负载分散到多台测试机，或用独立服务器入口压力工具测后台队列，并单独测真实浏览器显示时差，避免把一台机器的 80 浏览器过载当成真实实验客户端环境。
2. 追踪长 HTTP 事务、共享锁、Session/participant 数据序列化及结果轮询，缩短或错开等待。不要直接移除全局事务锁或增加 worker；锁前待处理注册表是进程内状态，任意多 worker 会破坏当前协议假设。
3. 依据目标人数的排队分布选择清空参数，并专门测试 T+59 秒集中到达、排队后处理、幂等、刷新和断线。仅将 10 改为更大的数不能解决晚显示导致实际决策时间变短的问题。
4. 复测 33 轮、H/HA 两套问卷、正式成本合计和现金复算。在准备完整验收前，本次没有进一步改业务代码，交由本地调整。
5. 验收通过后一起切换新 launcher 和环境开关，不能只给旧 `otree prodserver` 设置 `DYNAMIC_ROOM_RELEASE_PROTOCOL=1`；旧入口未安装锁前中间件，创建新会话会被保护逻辑拒绝。
6. 新协议标记仅在新会话创建时写入；不要把已经开始的旧会话半途切换。启用前再次备份并确认无真实参与者正在实验。

## 本地修改优先级

以下是定位和修改建议，不是本次已经实施的修复。优先保留当前机制的服务器可信入口时间、Session 统一截止、幂等和旧会话兼容，不要退回每人进入页面后单独倒计时。

| 优先级 | 工作项 | 代码定位与边界 |
| --- | --- | --- |
| P1 | 缩短 status/ACK 路径，先做耗时分解 | `dynamic_bottleneck_round/__init__.py:1787` 的 `room_release_state`、`:1821` 的 `room_release_snapshot`、`:4451` 的 `Decision.live_method`。检查纯状态查询是否重复标记并写回完整 Session.vars，以及逐组遍历成本；这些是源码可见的热点候选，尚未通过性能剖析证实为唯一根因。 |
| P1 | 复测真实可操作时刻和客户端负载 | `_static/dynamic_bottleneck_round/room_release.js:39` 的时钟校准、`:115` 的 activate。先分散测试负载，保留时间误差区间，不把 server_now_ts 与 T 的差当成浏览器真实显示延迟。 |
| P1 | 测清截止附近的 POST 排队并配置清空期 | `dynamic_bottleneck_round/decision_ingress.py:194` 的锁前采样与 pending 注册、`dynamic_bottleneck_round/__init__.py:4577` 的校验、`:4624` 的保存、`:2327` 的结果准备。入口时间决定是否准时；不能因处理开始晚就把有效决定变成超时补选。 |
| P2 | 检查结果轮询和结算是否放大跨房间等待 | `dynamic_bottleneck_round/__init__.py:2196` 的 `_set_results_locked`、`:2327` 的 `maybe_prepare_results`。记录 HTTP 锁等待、事务内 SQL/序列化、结果计算和 Agent 预取收集的分项耗时，再决定优化。 |
| P2 | 补全 operative 回执审计 | `dynamic_bottleneck_round/__init__.py:4451`。核对客户端展示后立即 POST/导航，与旧页 WebSocket operative 消息的到达顺序。缺失记录不能解释成参与者没看到页面；本次未定位缺失的唯一原因。 |

建议增加仅含会话、轮次和匿名参与者代码的性能日志，分别记录入口、锁获准、业务开始、事务提交和响应完成；不要记录 API 密钥、管理员密码或完整环境文件。日志采样/聚合本身也需要控制开销。

## 测试驱动修改与启用门槛

1. 先补失败测试，再修改实现。40 人和 80 人分开统计，I0/I1、H/HA、临近截止突发提交、HTTP/Live 混合请求均需覆盖。单纯改测试阈值不能证明修复。
2. 真实冻结 Player 的 Decision GET/POST 继续通过；旧自动决定、已结算决定和重复提交不能被覆盖；请求级临时状态不能跨参与者或跨轮次串扰。
3. 同一 Session 所有真人共享唯一 T 和 T+60，两个 Session 彼此独立；按现有设计，健康客户端应全部在 T 至 T+2 秒内获得可操作页面。不满足时需要明确技术异常处置，不能仍把该轮当作同步实验有效数据。
4. 在 T+59 秒前后发送集中 POST，区分锁前已到达与真正迟到；已到达且有效的选择应在清空期内正确保存为 manual。超出清空期要明确标记技术异常，不能默默生成被试缺席/掉线行为。
5. 清空期应依据实测的目标并发队列及安全余量确定。先验证参数，再写入生产；不在报告中武断指定一个保证安全的秒数。
6. 完成新协议 33 轮真实流程，检查 30 正式轮成本合计、H/HA 问卷必答与显示、Agent 记录唯一性、支付金额和最终结束页。不能沿用本次只到第 14/15 轮的证据宣称全流程通过。
7. 通过后才一起切换 `project_prodserver.py`、`DYNAMIC_ROOM_RELEASE_PROTOCOL=1` 和经验证的清空参数，并新建测试会话检查管理员创建路径；旧会话保持原协议。
