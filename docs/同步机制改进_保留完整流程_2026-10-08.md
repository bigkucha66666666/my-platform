## 保留的实验流程

仍为 3 轮练习、30 轮正式实验，共 33 轮。Introduction、ComprehensionCheck、WarmupStart、FormalStart、RoundStartSync、Decision、RecoveryGate、ResultsSync、Results 以及后续 H/HA 问卷、支付和结束页保持原流程。ResultsSync 继续等待同一 Session 内所有组结算；同步优化没有增加页面、缩短问卷或跳过支付。

每个 40 真人 Session 仍为 H 组 30 真人、HA 组 10 真人加 10 LLM 和 10 RL。两个 Session 仍分别拥有自己的准备屏障和唯一 T/T+60；Room、参与者标签、管理员监控和旧会话兼容保留。I0 决策期间不显示当前容量；I1 只在 T 到达后显示自己组的当前容量。

## 协议 2 的行为

Decision 原页面先加载外壳，再以签名令牌向同源 `/dynamic-room-sync` 发送 ACK/status/operative/decision。令牌绑定 Session、轮次、参与者、页面、外壳 nonce 与日志身份，不包含当前容量。控制请求在独立线程池读写小型 SQLite 日志，避免同步业务处理阻塞控制事件循环。

所有 oTree HTTP/Live 业务仍通过一个 ThreadedASGI 业务事件循环执行，保留 oTree 原生全局事务锁。业务没有改为多个 worker，也没有移除锁。默认控制线程数为 4；本次负载夹具刻意只使用 2 个控制线程。

完整有效请求体的可信时间、签名校验、选择校验和 pending 登记，在与最终结算关闭共用的短边界内完成；该边界没有数据库操作。登记和后台任务所有权先完成，才返回给 HTTP 等待方，避免请求体已接收但结算线程还看不到它。HTTP 等待方取消不能取消已经接纳的持久化工作。此前的网络/ASGI 调度延迟不属于这一进程内原子边界，也不能被解释为参与者本机点击时间。

前端每次控制请求的响应头和 JSON 正文合计最多等待 10 秒，超时中止该尝试并清理计时样本，再按原有有界重试机制重发；决策拒绝后的 status 探测也有相同限制。始终保留首次选择，迟到的旧响应不会重复提交表单或更新时钟。超时不会增加 60 秒可选择时间，也不会将尚未获得服务器回执的选择宣称为已保存。

有效决策先在 durable journal 提交，提交成功才返回接收确认；随后原生表单路径导入该 canonical receipt 并走原有结算。截止依据服务器完整请求体到达时间，不依据客户端时钟，也不依据业务开始处理时间。T+59 到达、T+61 才被业务消费仍可为 manual；真正到达 T+60 及之后的新决定为 late。重复发送、连接恢复以及原生表单中的第二个值不会覆盖首次有效接收值。

清空期针对独立控制选择的持久化和 pending 注册，并可等待缺失选择的自动确认，不增加可选择时间，也不是原生业务队列的总时长上限。已经保存的准时 manual 不会因后续原生业务排队超过清空期而改判迟到。超过清空期仍有控制决策 pending、当轮 Decision 相关 HTTP 故障、丢失日志或进程重启等技术异常，应明确记录并停止把该轮当作健康实验数据；不能将这些故障默默转换为缺席或自动补选。普通迟到及真实缺席沿用原有自动策略。日志的 settled 标记只在全部组业务成功提交后设置，提交回滚可重试且不会产生虚假的已结算标记；不能将任意 ResultsSync 请求失败一概解释为当轮 Decision 技术异常。

处理上限不依赖业务线程恰好观察到 pending。首次有效 manual 的控制持久化若超过 deadline+drain，仍保留其真实到达时间和选择，但标记 `decision_control_queue_overrun`、排除健康行为数据。日志处理时间和工作线程提交完成后的时间均检查，覆盖 SQLite 锁等待/提交延迟；故障处理完成后才释放 pending。已早先保存成功的 canonical 重放、普通真正迟到，以及慢原生业务消费不会因这条规则被反向判错。

合法且已认证的控制请求保存失败时，服务器在移除 pending 前锁定 `control_persistence_failure`，并在工作线程尝试持久化异常。即使写异常本身暂时失败，也不能在存储恢复后把丢失选择当作健康缺席补选。重试的 ACK/status/operative/decision 也必须持续报告技术异常，不能因其他读写已经恢复而发送健康响应；已存在的有效回执仍保留。

合法请求无法进入控制队列时锁定 `control_queue_admission_failure`，并合并至最多一个额外的排队/运行落盘任务，工作线程容量恢复后自动记录异常，不要求该房间再发请求。若存储持续不可用，保留待落盘标记与故障闩，在后续准入/容量恢复事件和关闭收尾时再尝试；不新增无限重试队列或空转定时器。所有数据库操作仍在工作线程，主控制事件循环不等待 SQLite。无效签名、身份和选择仍是校验拒绝，不据此污染整个 Session。

最终结算同时检查控制 pending 与故障。若故障发生在原生提交过程中、提交已经成功，保留实际已保存的选择与结果，但将该轮记为异常、不认证为健康 settled；不能假装已经提交的数据库事务还可回滚。日志结算标记失败也保留技术异常。成功结算关闭边界后的重放失败，不反向改写历史结果。

审计导出分别保留原生表单到达/业务处理/响应完成字段，以及新增 `room_release_receipt_ingress_ts`、`room_release_receipt_kind`，避免把控制回执延迟当作原生业务延迟。旧协议对应的新字段为空。

## 新会话开关和入口

仅新建 Session 时读取下面配置；不能在已开始的旧会话中途修改标记。无协议标记的历史会话继续原路径，marker 1 继续原生 Live 路径，marker 2 使用独立控制路径。

| 配置 | 要求 |
| --- | --- |
| `DYNAMIC_ROOM_RELEASE_PROTOCOL` | 新会话启用协议 2 时为 `2`；`1` 保留协议 1，未设置保持旧路径。 |
| `DYNAMIC_ROOM_RELEASE_DRAIN_SECONDS` | 必须依据目标人数并发实测配置；有限数且 `0 < 值 <= 120`。本地夹具的 10 秒不构成服务器参数建议。 |
| `DYNAMIC_ROOM_SYNC_DB` | 指向可写、持久、绝对 SQLite 文件路径；默认 `room_sync.sqlite3` 相对工作目录。建议配置固定的服务数据目录，避免临时目录或发布切换导致日志丢失。 |

正确入口为 `python project_prodserver.py [地址:端口]`，例如 `python project_prodserver.py 0.0.0.0:18000`。该 launcher 先执行标准 oTree setup，再加载 `project_asgi:app`，保持单 worker 和原 timeout subprocess。不要跳过初始化直接加载 ASGI，也不能仅向旧 `otree prodserver` 添加协议开关；创建时会检查入口中间件、控制传输和清空参数并拒绝不完整配置。

协议 2 日志应与业务数据库一起纳入服务运维。保持签名所需的原有 `SECRET_KEY`，不得在报告或测试输出中打印密钥、令牌或完整环境。当前实现依赖一个 worker 的进程内 pending 注册表；禁止用增加 worker 的方式解决排队，跨进程扩展需要另行设计和验收。

使用反向代理时，应保留正确 Host 和协议信息，并将同源 `/dynamic-room-sync` 路由转发到同一入口；需要在服务器隔离环境验证 Origin/Host/HTTPS 配置。不要通过放宽同源校验来掩盖代理配置问题。

进程内只缓存已核对的控制身份及允许的分钟集合，用于在队列已满时先拒绝非法请求；不缓存选择、时钟或结果事实。当前身份缓存上限为 32,768 个不同页面身份，达到上限会显式拒绝新增令牌，不偷偷淘汰仍活跃的身份。大量重复刷新或长期不重启的服务需要关注此限制；只能在没有活跃实验的维护窗口安排服务重启，不能在实验中重启来清理缓存。

## 日志备份与故障处理

日志使用 SQLite WAL 和 `synchronous=FULL`。运行时不能只复制主 `.sqlite3` 文件而忽略 WAL。可用 SQLite 在线备份 API 生成一致快照；同时保留业务 PostgreSQL 的备份。若需要二者处于一致实验边界，应在无活跃参与者、业务已清空的维护窗口备份。

下面是在线日志快照方法示意，路径由运维选择；不是本次已执行的服务器操作：

```python
import sqlite3
from contextlib import closing

with closing(sqlite3.connect('/absolute/persistent/room_sync.sqlite3')) as source:
    with closing(sqlite3.connect('/absolute/backups/room_sync.snapshot.sqlite3')) as target:
        source.backup(target)
```

日志有持久身份，Session 保存对应身份。文件被删除或替换时，已有 Session 不能初始化新日志并重新开始 T；应 fail closed 并核查原日志和备份。进程 boot 身份改变会将未完成轮次记为 `worker_restarted_during_round`；恢复日志不等于允许继续把已经故障的轮次当作正常数据。已经 settled 的记录保持历史结算状态。
