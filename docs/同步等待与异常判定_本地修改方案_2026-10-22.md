## 2. 三种现象要分开处理

| 现象 | 当前证据 | 处理方向 |
| --- | --- | --- |
| 结果结束后，下一轮约等 5–6 秒才可选择 | 已确认存在固定 5 秒放行提前量，6 轮单人浏览器记录一致 | 明确倒计时；确需缩短时，使用新 Session 保存的参数 |
| 人多时页面加载和同步等待增加 | 已确认重复 ORM 查询；原 80 人长测的批量决策页处理时间随轮数增长 | 先优化查询和无用数据加载，再测并发排队 |
| 一直“准备本轮结果”或出现“技术异常” | 存在真实浏览器停留记录；隔离长测也复现 `decision_page_http_failure` | 记录请求、事务、确认与跳转链路；不能把它视为正常 5 秒等待 |

这些证据不能支持“只是服务器配置低”“只是浏览器插件”或“换服务器即可修复”的结论。学校服务器本轮未连接或对照测量；旧服务器的历史长测也有相同异常类别，不能断言那里完全不存在这个问题。

### 2.1 人数增加为什么可能更慢

正常流程可拆为：

```text
结果页提交/到时
  → 服务器返回下一轮决策页
  → 浏览器渲染并发送 ACK
  → 同一 Session 的参与者就绪
  → 安排统一放行 T = 就绪处理时刻 + 5 秒
  → 浏览器收到到达 T 的状态，显示可选择内容
```

从某一参与者看，等待大致由“页面加载与排队、等待本房间就绪、5 秒放行提前量、状态确认及渲染”组成。各部分可能重叠，并非简单按人数线性相加。

人数增加会增加请求量，也增加较晚就绪者出现的机会；两个 Session 独立同步，不建立跨 Session 屏障，但共享一个业务 worker 和数据库资源。

准备期限通常为首轮 120 秒、其余轮 60 秒。这是准备超时的判定边界，不是每轮必须等满的时间：确认齐全就会安排放行。缺席、已渲染但未 ACK、请求尚在排队等情况有不同处理，不能统一跳过。

### 2.2 实际计时

2026-10-22 新 ECS 的单人浏览器验收记录中，六轮均有：

- 最后一个 ACK 到计划放行约 `5.001` 秒。
- ACK 到浏览器报告可操作约 `5.116–5.843` 秒。
- 近期结果页提交及下一轮决策页 GET，Nginx 记录的服务器处理约 `30–40 ms`。这是服务器侧耗时，不是完整浏览器导航耗时。

因此，刚才用户感受到的几秒等待，主要有固定放行提前量这一明确来源。人数更多时的额外等待仍需按房间测量。

## 3. 第一步：减少重复查询，不改变同步判定

### 3.1 已定位的位置

文件：[sync_integration.py](/Users/hybsmac/Python项目/economics-experiment/my_platform/dynamic_bottleneck_round/sync_integration.py)，函数 `state()`，调用 `runtime.bind_native_round()` 的位置。

现有实现：

```python
runtime.bind_native_round(session.code, number,
    [p.participant.code for p in player.subsession.get_players()],
    result['decision_page_index'], settled=result['settled'])
```

一次决策页 GET 的分析中，`state()` 被调用 7 次；在 40 人房间中，这种逐 Player 访问 Participant 的方式反复触发延迟加载。后期样本记录了约 276 次参与者主键加载，单次页面约 292 次 SQL 执行。

最小候选改动：

```python
runtime.bind_native_round(session.code, number,
    [p.code for p in session.get_participants()],
    result['decision_page_index'], settled=result['settled'])
```

这个改动适用于当前应用每轮包含同一 Session 全体参与者的结构。它只改变身份列表的查询方式；若将来存在只覆盖 Session 部分参与者的应用，需要按该轮 Player 与 Participant 的关联筛选，不能直接沿用全部 Session 身份。

必须保留所有席位的故障映射，包括本轮已暂停或不在 `expected_codes` 中的参与者。不能直接把故障映射改成只有 `expected_codes`，否则可能漏掉迟到原生请求。

### 3.2 候选补丁及已知效果

补丁：[cohort-query-optimization.patch](/Users/hybsmac/Python项目/economics-experiment/my_platform/output/deploy_ecs_20261022/cohort-query-optimization.patch)。它包含上述一行性能修改，以及查询数量/身份覆盖的回归测试。补丁未应用到当前业务工作区，也未发布到线上。

新增测试在修改前以“一次已初始化 cohort 查询产生 42 次 SELECT”失败，修改后通过；同时检查完整 40 人故障映射和 30 人资格集合仍分别保留。另有首个原生请求故障、原生请求失败阻止结算、暂停与恢复三项相关测试通过。

在失败验收库的独立副本上，带 cProfile 的一次后期页面测量中，SQL 执行由约 292 次降至 18 次，页面样本由约 0.428 秒降至 0.305 秒。该测量包含性能分析开销，且不是统计充分的并发基准；不能据此承诺 80 人端到端提速比例。

`session.get_participants()` 仍会载入完整 Participant，包括逐轮累积的变量。后续可在本地比较“只查询参与者 code 列”或“请求范围内复用不变身份列表”，进一步减少无用反序列化；这部分尚未实现和验证，不包含在补丁中。

避免把整个 `state()` 的返回值全局缓存：ACK、故障、资格、截止时间和结算状态可能在并发请求中改变。只有身份列表等已证明不变的数据适合复用，并须保留数据库/Session/轮次边界。

## 5. 第三步：异常分类先补证据，再决定是否改判定

### 5.1 当前失败链路

相关位置：

- [test_room_release_framework.py](/Users/hybsmac/Python项目/economics-experiment/my_platform/dynamic_bottleneck_round/test_room_release_framework.py)：`http_request()` 用 `asyncio.wait_for(..., timeout=20)` 限制测试请求。
- [sync_transport.py](/Users/hybsmac/Python项目/economics-experiment/my_platform/dynamic_bottleneck_round/sync_transport.py)：`ThreadedASGI.__call__()` 在外层取消后继续排空原生 HTTP，避免 ORM 回调仍运行时释放业务锁。
- [decision_ingress.py](/Users/hybsmac/Python项目/economics-experiment/my_platform/dynamic_bottleneck_round/decision_ingress.py)：异常/取消会进入 `raised` 路径，交由原生请求故障保护处理。
- [sync_runtime.py](/Users/hybsmac/Python项目/economics-experiment/my_platform/dynamic_bottleneck_round/sync_runtime.py)：`finish_native_request()` 对关联轮次锁存 `decision_page_http_failure`。

原版本 80 人 PostgreSQL 测试中，第二房间批量决策页处理从首轮约 9.949 秒增长至第 28 轮约 19.409 秒，第 29 轮最后渲染约 19.948 秒，随后 ACK 被技术异常保护阻止。整个进程耗时约 1661.1 秒，未触及 2600 秒总预算。

这些证据指向批量串行处理接近测试请求 20 秒取消边界。仍需记录该次取消的精确时点、响应完成和事务提交结果，才能进一步区分测试取消、传输失败与业务失败；不能只凭 200 响应头就证明业务已经成功提交。

真实浏览器的长时间停留也不能直接等同于上述测试超时。曾出现 ResultsSync POST 已返回 302、浏览器未及时发起下一页 GET 的情况，需要另看导航、WebSocket 自动推进和浏览器环境的时间线。

### 5.2 本地增加的观测项

按 Session、轮次、参与者及请求关联号记录以下时点，避免写入密码、令牌、选择内容或完整请求正文：

| 边界 | 建议观测 |
| --- | --- |
| 请求 | 到达、等待业务锁、取得锁、回调开始/结束 |
| 响应和事务 | 响应头状态、响应体结束、事务提交/回滚、异常类型、取消时间、排空结束 |
| 同步 | shell 渲染、ACK 到达/落盘、预期/已确认数量、放行 T、operative 到达 |
| 页面推进 | 原页 POST、302、目标页 GET、目标页 ACK，分别计时 |

原始排队、取消和失败原因应保留为审计字段，不只留下一个笼统异常名。结果页本身的停留时长单独计量，不计作服务器跳转延迟。

### 5.3 哪些异常不能自动恢复

当前不建议移除 `raised` 判断，也不建议把取消一律视为成功。若后续确需细分状态，最低边界为：

- 原生 5xx、事务回滚、提交状态未知、控制回执持久化失败、超过 drain 仍未完成的请求，继续阻止正常结算。
- 已在服务端渲染但未 ACK，与完全未到场不能归为同类；前者可能是传输或页面异常。
- 重复/过期请求按身份、页索引和当前轮校验，不覆盖已接受回执，不生成第二份人工选择。
- 只有在请求排空、业务事务成功、完整响应与轮次归属都有可靠证据后，才研究是否把单纯传输断开另行分类；即使分类改变，也不等于可以自动解除已持久化的技术异常。
- 既有 `TECHNICAL_ANOMALY` 场次保留原记录；不清空 journal、不 Admin Advance、不创建替代身份掩盖故障。新机制先用新 Session 验证。

### 6.2 必须补齐的验证矩阵

| 场景 | 需要证明 |
| --- | --- |
| 1 人、40 人、两房间 80 人 | 分别记录结果提交到 GET、GET 到 ACK、最后 ACK 到 T、T 到可操作；报告中位数、P95 和最大值 |

| 完整 33 轮 | 所有轮次、两页问卷、完成和付款均通过，保留逐轮耗时；最后几轮不能跳过 |

| 取消/断网、5xx、回滚 | 请求被正确排空，故障继续保护结算；重复提交幂等 |
| 5 秒与新 3 秒方案 | 仅新 Session 改变提前量；旧 Session、已安排 T 与截止时间保持原值 |
| 浏览器 | 正常窗口与无扩展窗口分别测；I1 信息不提前泄露，T 前不可操作，截止后不可接受人工选择 |

PostgreSQL 验收须新建明确的空测试库，并与生产库及生产 journal 隔离。原完整流程 fixture 对组返回顺序使用了列表下标假设；PostgreSQL 适配只可按 `id_in_subsession` 排序后保留原断言，不能放宽人数、人工记录或结算断言。

保留原 20 秒请求预算作为性能回归指标。若另做更长观察预算的诊断运行，应分别报告，记录实际请求时间和超预算次数；不能只延长测试时间后宣称性能已修复。实验的准备、决策、结果、drain 时间不得随测试预算调整。

现有 full-flow 外层也有独立进程预算，本机入口常见为 1200 秒。触及总预算时应报告实际失败位置；不要混淆进程预算、单请求 20 秒预算和实验业务截止时间。

### 6.3 诊断不得推进正在使用的身份

参与者页面 GET 可能启动准备时钟并写状态，不能用生产参与者 URL 做 curl 延迟探针。常规网络探针使用 `/login`、静态资源或健康端点；页面流测试使用标注清楚的独立验收 Session，并由真实浏览器正常推进。

本轮曾误用原验收身份的 GET 探针，导致它提前进入下一轮而没有浏览器 ACK，随后形成技术异常。这一诊断引入的异常与先前结果页停留分别保留，不用于证明服务器自身故障。该身份未被强制推进或清除异常。
