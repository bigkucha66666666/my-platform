# 新服务器依赖与启动说明

## 版本差异的原因

原 requirements.txt 使用 `otree>=5.11,<6.0`，排除了本地 conda 的 oTree 6.0.13；旧服务器排查记录为 Python 3.10 / oTree 5.11.5。因此，复制代码并不能统一框架版本，也不能据此断定两端业务代码完全一致。旧服务器的当前实际版本、代码和数据库仍需部署前重新核对。

新服务器改用 **Python 3.10 / oTree 6.0.13 / psycopg2-binary 2.9.10**，不把整个 conda 环境的无关包导出。oTree 的发布元数据已固定其直接依赖，包括 Starlette 0.14.1、SQLAlchemy 1.3.22、uvicorn 0.13.4、websockets 10.1；不要单独升级这些框架内部依赖。

清单对应当前实验运行，不额外加入未使用的 pandas、NumPy、Redis 等。原生命令行 browser bots 的 requests/ws4py、可选 Sentry 不属于这份最小运行清单；尤其不要在未配置兼容 SDK 时复制启用 `SENTRY_DSN`，否则 oTree 初始化会要求缺少的可选依赖。固定旧框架的兼容版本不等于依赖已通过全面安全审计；正式联网仍需访问控制、反向代理和后续安全维护。

`requirements.txt` 同时引用 `requirements-lock.txt`，后者固定这次独立安装解析出的全部 15 个运行时包版本，包括间接依赖 click、h11 和 six。**部署时两个文件都要复制**，仍只需运行一次 `pip install -r requirements.txt`。这是版本约束文件，不是带哈希的构建锁；操作系统、架构、Python 和构建工具仍会影响二进制产物。新服务器首次验收通过后，应保留 `python -m pip freeze` 输出、Python 版本、Git 版本和启动配置，供后续同平台复现。

## 在新服务器的独立环境安装

先将项目复制到新目录，使用 Python 3.10 创建专用环境；不要覆盖原服务器环境。若使用 conda：

```sh
conda create -n otree_server python=3.10
conda activate otree_server
cd /你的新服务器项目路径/my_platform
python -m pip install -r requirements.txt
python -m pip check
python -c "import sys, importlib.metadata as m; print(sys.version); print({n: m.version(n) for n in ['otree', 'psycopg2-binary', 'starlette', 'sqlalchemy', 'uvicorn', 'websockets']})"
```

生产环境的 DATABASE_URL、管理员账号、API 配置、Room 标签文件、同步日志路径必须另外核对；requirements 不会迁移这些配置。不要把密钥或含凭据的环境输出写入公开日志。

生产启动前必须通过受限权限的服务环境配置设置 `OTREE_PRODUCTION=1`、`OTREE_AUTH_LEVEL=STUDY`、独立高强度的 `OTREE_SECRET_KEY` 和 `OTREE_ADMIN_PASSWORD`。当前项目在 settings.py 固定管理员账号为 `admin`，`OTREE_ADMIN_USERNAME` 并不生效；本次没有替你更改账号。新服务器不得沿用开发默认密钥或空密码；不要把真实密钥写进本文、Git 或终端截图。项目在缺少生产标志时会开启 DEBUG，因此不能仅安装依赖后就开放公网。迁移旧服务时，现有密钥的保留或轮换需另行规划，不能擅自替换以致已有登录和签名失效。

正式启用项目同步机制时使用项目入口，保持 **单个 web 实例、单业务 worker**，不要改成裸 `otree prodserver`、多 worker 或多个 web 实例共同运行同一场次；并配置 `DYNAMIC_ROOM_RELEASE_PROTOCOL=2` 和固定、可写且可持久化的 `DYNAMIC_ROOM_SYNC_DB` 路径：

```sh
python project_prodserver.py 127.0.0.1:8000
```

应由进程管理器保持服务，并通过反向代理提供 HTTPS / WebSocket。不能同时保留重复实例占用同一数据库或同步日志。完成本文环境安装不代表并发同步验收已经完成。

启动器的 finally 可在正常退出或异常退栈时回收超时子进程，但进程被 SIGKILL 时无法执行清理；systemd 应保留 `KillMode=control-group` 等整组回收策略。停止旧服务后确认旧 worker 已退出，再启动新实例。

仓库的 `Procfile` 也统一为上述项目启动器，仅一个 `web` 进程定义（默认读取平台的 `PORT`）；项目启动器会自行创建并回收一个可信超时子进程。不再使用旧的 `prodserver1of2` / `prodserver2of2` 两进程定义。若使用 systemd，应继续由 systemd 启动项目入口，不同时再启动 Procfile 服务；这次修改没有替你改动任何服务器的进程配置。

systemd 的 WorkingDirectory 应为实际项目根目录 `my_platform`，ExecStart 使用所选 conda/venv 环境中 Python 的绝对路径，不依赖交互式 `conda activate` 或 PATH 中另一个 `otree` 命令。项目超时子进程已使用主服务的 `sys.executable` 启动，避免主/子进程再落到不同环境。

## 数据迁移与验收边界

迁移旧 Session 前，先停止新增实验并确认无人实验，备份业务数据库、同步诊断数据库、Room 标签文件、配置和当前发布代码，验证备份可恢复。**不要执行 resetdb，不要直接让 6.0.13 接管唯一一份 5.11.5 数据库。** 先在隔离副本验证框架升级、旧 Session 查看和全轮次导出，再决定正式迁移；这次本地修改未执行生产数据库迁移。

同步 SQLite 应停机后备份，或使用 SQLite 在线备份接口生成一致快照；不能在活动时只复制主文件而忽略 WAL，也不要手改 journal identity 来强行匹配旧 Session。

若只开展新实验，也应使用独立新数据库和新的同步日志，保留旧数据库供旧数据查询，不把两个版本同时指向同一份业务数据。不同平台编译旧版 MarkupSafe 等依赖时可能需要构建工具；不要为了绕过安装错误而任意放宽框架版本。

上线前至少检查管理员登录、创建 Session、Room 标签进入、I0/I1 分组、同步放行、真人提交、Agent 回退、3 轮热身加 30 轮正式、问卷、报酬和按 Session 导出。隔离 SQLite 回归不等同于 Linux/PostgreSQL、多设备和真实并发验证。
